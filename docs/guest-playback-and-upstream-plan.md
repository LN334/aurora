# 上游包与免登录播放方案

> 写于 2026-11-17。所有结论来自本机实测（装包、发真请求、看返回），不是读文档猜的。
> 读者不需要会写代码——本文只回答「改不改、改了有什么变化、风险多大、你怎么验」。

---

## 一、先说结论

**不建议换任何上游包。** 你的四个音乐平台里，三个已经在用社区维护的上游包，酷狗是把第三方源码整包搬进来。这套结构是对的，换包只会增加维护面，不会让用户多听到一首歌。

**真正值得改的只有一件事：酷狗现在没登录就完全不能播，但实测免费歌不登录也能播。**

| | 现在 | 改后 |
|---|---|---|
| 没登录酷狗，点免费歌 | 弹「酷狗需要登录账号后才能取到播放地址」 | 直接出声（128k） |
| 没登录酷狗，点 VIP 歌 | 同上 | 仍然提示要登录（不假装能播） |
| 登录后 | 不受影响 | 不受影响 |

工作量半天以内，风险低：兜底源挂了就走回现在这条路。

## 二、现在是什么状况

你的应用背后这些代码：

| 平台 | 背后是谁 | 代码量 | 月下载 | 最近更新 |
|---|---|---|---|---|
| 网易云 | `@neteasecloudmusicapienhanced/api` 4.41.1 | 适配层约 2,000 行 | 5,169 | 2026-10-05 |
| QQ 音乐 | `@sansenjian/qq-music-api` 2.6.0 | 适配层 3,421 行 | 263 | 2026-08-27 |
| 酷狗 | `vendor/KuGouMusicApi`（源码整包搬入） | 17,315 行 + 适配层约 2,300 行 | — | — |
| 汽水 | `qishui-music-api` 0.2.2 | 适配层约 1,500 行 | 1,208 | 2026-10-22 |

**一处需要纠正的说法**：之前那份调研报告里写「QQ 自研约 3,000 行」，不准确。那 3,421 行是**适配层**（签名和协议在 `@sansenjian/qq-music-api` 包里），不是自己重写的协议。酷狗不一样，酷狗是真的把别人的整个服务端源码搬进来了。

差别在哪：换成上游包，出问题可以等作者更新；搬源码进来，出问题只能自己改。

## 三、我实测了什么

装了 npm 上的候选包，发了真请求：

**① 酷狗能免登录拿到流**

```
GET 206  content-type: audio/mpeg
content-range: bytes 0-2047/4217901
magic: 494433（"ID3" 音频帧头）
```

4.2 MB、128k、能播。用的是 `@meting/core`，不需要任何账号。

**② QQ 换包没有收益**

拿同一首歌，分别用你现用的 `@sansenjian/qq-music-api` 和候选的 `qqmusic-api-enhanced` 请求播放地址，两边返回的 `purl` 字段**都是空的**（`midurlinfo[0].purl = ""`）。这是 QQ 音乐自己的限制：不登录不给流，跟用哪个包无关。

**③ QQ 的试听片段是空壳**

上游确实返回了试听字段（`testfile2g`）和一堆带 vkey 的链接，但我把四个 CDN 域名都拼了一遍，返回的全是：

```
206  audio/mp4  total=100 字节
```

100 字节的空 m4a，有文件头没音频。所以代码里那句「上游不给试听片段」是对的，这条路走不通，别惦记。

## 四、建议做的那件事

### 改哪里

只有一处：`electron/kugou/client.ts` 第 825 行。

现在是：

```ts
if (!state.token) {
  return { ok: false, reason: 'login-required', ... }   // ← 直接放弃
}
```

改成「先试兜底，兜底也不行才放弃」。

### 具体怎么做

1. 新建 `electron/kugou/fallback.ts`：用 `@meting/core` 做一次「搜索同名歌 → 取 128k 直链」。
2. `client.ts` 的 `login-required` 分支改成：先调兜底，成功就返回，失败才返回原来的错误。
3. `package.json` 加一个依赖 `@meting/core`（零依赖，压缩后几百 KB）。

### 你会看到什么

没登录酷狗时，点一首免费歌能直接播；点 VIP 歌还是提示要登录。界面不用动。

### 风险

| 风险 | 程度 | 兜底办法 |
|---|---|---|
| 兜底源只有 128k | 中 | 只在「没登录」时用；登录后走原来的 320k/无损 |
| `@meting/core` 月下载只有 478，不算热门 | 低 | 它只是个兜底，挂了走回老路，主流程不受影响 |
| 兜底搜索可能匹配错歌 | 中 | 用歌名 + 歌手双重比对，不匹配就放弃（宁可播不出，不能播错） |
| 酷狗改接口 | 低 | 主路径没动，兜底失效而已 |

### 怎么验收

1. 在应用里退出酷狗账号
2. 搜一首免费歌（例如「卡农 钢琴版」）点播放 → 应该出声
3. 再点一首 VIP 歌（例如周杰伦的晴天）→ 应该提示要登录，不能是静默失败
4. 重新登录 → 随便点一首 → 应该还是原来的高品质，没被兜底抢走

## 五、不建议做的，以及为什么

**换 QQ 上游包。** 候选包 `qqmusic-api-enhanced` 确实很干净（零依赖、把签名函数直接导出），但它缺 6 类接口：歌单增删改、每日推荐、新歌、收藏专辑、关注歌手、收藏歌曲。要补齐就得自己写协议——把「等作者更新」换成「自己维护」，方向反了。

**换掉酷狗那 17,315 行。** npm 上没有能顶替的包。`@meting/core` 一共只有 8 个方法（搜索/歌曲/专辑/歌手/歌单/取流/歌词/封面），而你的酷狗适配层用了 28 个（含登录、我的歌单、收藏、关注、每日推荐、歌单增删改）。它只能当兜底，不能当主力。

**换网易云。** 现用的包月下载 5,169，是同类里最活跃的，没有换的理由。

## 六、可选：加一道「上游变没变」的提醒

社区包最怕的是「作者不更新了，某天平台一改版全挂」。

可以在打包时跑一个小脚本，去 GitHub 拉上游最新 commit 的指纹，跟上一次记下来的比对。变了就在打包日志里提示一句「QQ 上游变过，发版前测一下」。不改代码逻辑，纯提醒。约 30 行，可选。

## 七、你需要做什么

1. 看完这份方案，决定做不做第四条那件事。
2. 如果做，我改完之后你只需要按「怎么验收」那 4 步点一遍。
3. 如果你不想动酷狗，那就什么都不用做——现在的架构是健康的，不换包也不会坏。

## 附：本文提到的实测命令结果

- 候选包安装：`npm i @meting/core qqmusic-api-enhanced`（2 个包，2 秒，零传递依赖）
- 酷狗搜索（meting）：返回统一格式 `{id, name, artist, album, url_id, source}`
- 酷狗取流（meting）：`{url: "http://fsios.tx.kugou.com/.../pi3_ct330700_s412093799.mp3", size: 4217901, br: 128}`
- QQ 取流（sansenjian，匿名）：`midurlinfo[0].purl = ""`
- QQ 取流（qqmusic-api-enhanced，匿名）：`data[0].url = ""`
- QQ 试听（sansenjian，匿名）：`testfile2g` 有值，但四个域名全部返回 100 字节空文件
