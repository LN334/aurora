# 第 4 站：工程化 —— 测试、构建与闸门

> 目标：能跑 `npm run check`，红了知道红在哪、为什么红。
> 预计：与第 3 站并行，3–4 周。

## 一、要解决什么问题

代码能跑只是及格。一个 9 万行的项目要能**一直**跑下去，靠三样东西：

1. **类型**：写错的时候立刻知道（tsc）；
2. **测试**：改坏的时候立刻知道（`node --test`）；
3. **闸门**：死代码、死样式、坏引用积累不起来（四项审计）。

这一站就是这三样。它看起来最不「酷」，但它是这个项目能在一个月里从 0 长到 682 个提交的原因。

## 二、为什么需要「构建」

浏览器（和 Electron 的渲染进程）只认 JavaScript、HTML、CSS。你的源码里有 `.ts`（类型标注）、`.tsx`（JSX）、`import './x.ts'`（带扩展名的 ESM）——它看不懂。

所以要有一步「翻译」。这个项目有**两条翻译线**：

| 代码 | 翻译工具 | 产物 |
| --- | --- | --- |
| `electron/**/*.ts`（主进程） | `tsc` | `dist-electron/*.js` |
| `src/**/*.ts(x)`（渲染层） | Vite（内部用 esbuild/Rollup） | `dist/assets/*.js` |

`npm run dev` 会同时跑它们，`npm run build` 会依次跑它们。

### 两个 tsconfig 为什么不一样

```jsonc
// tsconfig.json —— 只管类型检查，不产出文件
{
  "compilerOptions": {
    "module": "ESNext",
    "moduleResolution": "bundler",   // 按 Vite 的规则找模块
    "jsx": "react-jsx",
    "noEmit": true,                  // 只检查，不编译
    "types": ["vite/client"]
  },
  "include": ["src"]
}
```

```jsonc
// tsconfig.electron.json —— 真编译，产物给 Electron 跑
{
  "compilerOptions": {
    "module": "nodenext",            // 按 Node 的规则输出
    "moduleResolution": "nodenext",
    "outDir": "dist-electron",
    "rootDir": "electron",
    "allowImportingTsExtensions": true,
    "rewriteRelativeImportExtensions": true,
    "types": ["node"]
  },
  "include": ["electron/**/*.ts"]
}
```

关键在于**它们的运行环境不同**：渲染层由 Vite 打包，找模块的规则宽松；主进程由 Node 直接执行，规则严格。同一份配置糊两个环境，必有一个出错。

`allowImportingTsExtensions` 那一对选项，注释写了原因：

> `node --test` 直接把这些文件当 TypeScript 跑，所以测试里 import 必须写全 `.ts`。只允许这种写法，编译出来的 JavaScript 会把扩展名改回 `.js`。

这就是「工程化」的样子：**每一条奇怪的配置背后都有一个具体的痛苦**。找到那条注释，就理解了那个决定。

## 三、Vite：为什么它不只是「打包工具」

看 `vite.config.ts` 里的三个决定：

### 1. `base: './'`

```ts
// Relative base matters: the production build is loaded over file://
base: './',
```

生产环境页面是 `file://` 打开的。绝对路径 `/assets/x.js` 在 `file://` 下会指向磁盘根目录，直接 404。相对路径才对。

**一个字符的错误，整个打包版白屏。** 这种坑只能靠配置注释传下去。

### 2. 三个入口

```ts
input: {
  index: resolve(__dirname, 'index.html'),
  overlay: resolve(__dirname, 'overlay.html'),
  chat: resolve(__dirname, 'chat.html')
}
```

桌面歌词窗和聊天窗是独立的 `BrowserWindow`，各自一份文档。如果只声明 `index`，另外两个窗口会加载整个播放器——白耗几百 KB 和一堆初始化。

### 3. `manualChunks`：把 React 单独分出来

```ts
manualChunks(id) {
  if (!id.includes('node_modules')) return undefined
  if (/[\\/]node_modules[\\/](react|react-dom|scheduler)[\\/]/.test(id)) return 'vendor-react'
  if (/[\\/]node_modules[\\/](webwallgl|mediabunny)[\\/]/.test(id)) return undefined  // 留给懒加载
  return 'vendor'
}
```

注释说得很清楚：不指定的话，Rollup 会把 237 KB 的 React 运行时命名成 `icons-*.js`（因为它碰巧先扫到图标文件），构建报告完全读不懂。更重要的：**明确分块后，改业务代码不会让用户重新下载框架**。

`webwallgl`（壁纸引擎，1 MB 的 WebGL）特意**不**分进 vendor——它只被动态 `import()` 用到，让没开壁纸的用户永远不下载它。

这三个决定，每个都能单独写一篇文章。**读构建配置就是在读项目的历史**。

## 四、测试：为什么这个项目的测试不用 Electron

`npm test` 跑的是：

```json
"test": "node --test \"tests/**/*.test.ts\""
```

没有 Jest、没有 Vitest、没有配置。Node 24 直接读 `.ts` 文件，把类型标注擦掉就跑。

代价是：**测试文件不能 import 任何 Electron API**。这就是那条硬规则——

> `electron/pure/` 里不许 import Electron，否则裸 Node 测试加载不了。

于是项目长出了一批「为可测而拆」的文件：`invite-arg.ts`（12 行）、`crossfade.ts`（15 行）、`app-paths.ts`（36 行）、`boot-steps.ts`、`scan-progress.ts`、`lyrics-match.ts`……

**这不是过度设计，是让「难测的东西」变成「一个纯函数 + 一层薄壳」。** 举个最漂亮的例子：

```ts
// electron/pure/app-paths.ts —— 路径穿越防护，纯函数，可测
export function resolveAppAsset(root: string, requestPath: string): string | null
```

没人能对着「真的发一个恶意 URL 给 Electron 协议处理器」写单元测试。但对着上面这个纯函数，能写十条。

### 测试长什么样

```ts
// tests/crossfade.test.ts
import assert from 'node:assert/strict'
import test from 'node:test'
import { swapFadeMs } from '../src/features/player/crossfade.ts'

test('0 means hard cut, not a 190ms fade', () => {
  assert.equal(swapFadeMs(0), 0)
})

test('junk never reaches the audio clock', () => {
  assert.equal(swapFadeMs(-2), 0)
  assert.equal(swapFadeMs(Number.NaN), 0)
  assert.equal(swapFadeMs(Number.POSITIVE_INFINITY), 0)
})
```

四件事：`import test`、`import assert`、一个描述性的名字、一句断言。

**测试名是第一人称的句子**，读起来像需求：「0 意味着硬切，不是 190ms 淡出」「垃圾值永远到不了音频时钟」。这个项目的测试名全都这么写——它们是给人看的。

### 什么时候该写测试

项目的规则（`CONTRIBUTING.md`）：**新增纯函数尽量配一条用例。**

判断标准很简单：**这个函数如果算错了，用户会不会察觉？** 会，就值得测。`swapFadeMs` 算错了，用户会发现「滑到 12 秒和 1 秒没区别」——这正是它当初的 bug。所以它被拆出来、测了。

反过来，一个「把两个字符串拼起来」的组件不值得测。

## 五、四项审计：这个项目最特别的地方

`npm run check` 的最后一步：

```json
"check": "npm run typecheck && npm run test && node scripts/audit-reachability.mjs && node scripts/audit-css.mjs && node scripts/audit-stale-paths.mjs && node scripts/audit-exports.mjs"
```

四个脚本，各自拦一类「腐烂」：

| 脚本 | 拦什么 | 判据 |
| --- | --- | --- |
| `audit-reachability.mjs` | 从没被加载过的源文件 | 从入口（两个 HTML、main、preload、测试）走 import 图，走不到的报出来 |
| `audit-css.mjs` | 从没被命中的 CSS 选择器 | 对比源码里出现的 class 名与样式表里的选择器 |
| `audit-stale-paths.mjs` | 指向已不存在文件的路径 | 从代码里抽出路径字面量，`existsSync` 一遍 |
| `audit-exports.mjs` | 只在本文件里用过的 `export` | 去掉那个 `export` 关键字，全仓还剩几处引用？零处就是多余的 |

### 为什么不用正则

`audit-reachability.mjs` 开头专门解释了：

> Uses TypeScript's own parser rather than a regex, because a regex over `import` lines reports false positives for dynamic imports, type-only imports and re-exports - the exact cases that matter when deciding what to delete.

**这句话是整套工程化哲学的浓缩**：一个会误报的闸门，最终教会所有人忽略闸门。所以宁可多写点代码用真解析器，也不许有一次假红。

### 为什么这些闸门值得存在

因为**删除是最难的事**。一个文件没人 import 了，你还留着，一年后没人敢删（不知道谁在用）。四个脚本把这个判断自动化了，于是「删」变成一件安全的事。

项目在 2026-10 到 11 月做了好几轮「死代码清理」，每次都有 CHANGELOG 记录删了多少——这些审计就是那次清理留下的制度。

### 一条不能破的规矩

`CONTRIBUTING.md` 写道：

> 别为了让它们过而加 `// audit-ignore` —— 仓库里没有这个机制，该删就删。

**闸门如果没有例外通道，它才真是闸门。**

## 六、打包：从源码到安装包

```json
"dist": "npm run build && electron-builder --win"
```

`package.json` 的 `build` 段全是打包配置。挑四处看：

### 1. `files`：哪些东西进安装包

```json
"files": [
  "dist/**/*",
  "dist-electron/**/*",
  "assets/**/*",
  "!**/*.map", "!**/*.ts", "!**/*.md", ...
]
```

先全排除再补回。注意 `!**/*.ts`——TypeScript 源码不进安装包。

### 2. `asar: true` + `asarUnpack`

Electron 会把应用代码打成一个 `app.asar` 归档。但有些包**必须**是真文件（要 `child_process` 去 spawn、要读自己目录下的资源）：

```json
"asarUnpack": [
  "node_modules/music-metadata/**",
  "node_modules/@yakult-green-tea/qq-music-api/**"
]
```

### 3. `extraResources`

酷狗的后端是一个独立的 Node 服务（`vendor/KuGouMusicApi`），它不能被打进 asar（要真目录、要自己的 node_modules），所以走 `extraResources` 复制到安装目录旁边。

**一个应用里有第二个运行时进程**——这种事只有干过一遍才知道该怎么配。

### 4. NSIS 安装器

```json
"nsis": {
  "oneClick": false,                    // 给用户「下一步」的机会
  "perMachine": false,                  // 装到用户目录，不需要管理员
  "language": "2052",                   // 简体中文
  "installerSidebar": "build/installerSidebar.bmp"
}
```

安装器界面用自定义位图，不是默认的灰盒子。这一步属于「产品」不属于「工程」，但它同样写在一个 JSON 里。

### 发版是另一回事

打包（`npm run dist`）只产出安装包。发版还要：改 `version` → 打 tag → 建 GitHub Release → 上传三个附件（`Setup.exe`、`.blockmap`、`latest.yml`）→ 用 `latest.yml` 给自动更新做对账。

**这个项目的规矩：发版前必须问维护者。** 你自己练习时只 `npm run dist` 玩玩就好，别去建 Release。

## 九、练手

**练手 1（20 分钟）**：跑 `npm run check`，计时。然后故意改坏一个文件（比如把 `crossfade.ts` 的返回类型改成 `string`），再跑，看它红在哪一步、报什么。改回来。

**练手 2（30 分钟）**：跑 `node scripts/audit-exports.mjs`，随便挑一条它报的「多余导出」。**不要删**，先想：删掉会怎样？然后删掉，跑 `npm run check`，再 `git checkout -- <那个文件>`。

**练手 3（1 小时）**：给自己新写一个纯函数 + 一个测试。建议做「把秒数格式化成 `03:45`」这种小事（项目里已有 `src/ui/format.ts`，别看它，自己写）。要求：`node --test` 能跑过，且函数放在能被单独 import 的位置。

**练手 4（30 分钟）**：读 `scripts/audit-css.mjs` 的判据，回答：什么情况下它会**误报**一个其实在用的选择器？（提示：拼接出来的类名、只在注释里出现的类名）
