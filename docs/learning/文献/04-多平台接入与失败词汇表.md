# 文献 4 · 多平台接入与失败词汇表

> **读这篇之前**：读完第 2 站（联合类型）和第 4 站（IPC 与抽象接口）。
> **读完之后**：你能回答「为什么接入第六个平台不该改界面代码」，以及「为什么 VIP 歌不该标成『已下架』」。

本篇以 `src/features/online/types.ts`（637 行）和 `registry.ts`（161 行）为教材。这两个文件加起来只有 800 行，**是整个多平台能力的宪法**——五个平台的实现都在这套契约下面。

## 一、真正的难题不是「接一个平台」

接网易云，写一段 HTTP 请求、解析 JSON、拿播放地址。这只是一个下午的活。

真难题是**接第二个、第三个**。因为第一个平台写法一落地，界面里就长出了这种东西：

```ts
if (track.source === 'netease') { ... }
if (provider === 'qq') { showVipBadge() }
if (platform === 'kugou') { hideDailyRecommend() }
```

这些分支每一个都错得不明显。等接到第四个平台，同一个功能要在四处补 `if`——而且**没人记得要补**，于是新平台一进去就有几个按钮是坏的。

`types.ts` 开头的注释把这一层的设计目的说得很清楚：

> Three structural decisions are copied from it deliberately, because each one removes a class of `if (provider === ...)` from the UI.

**目标不是「代码好看」，是「界面里不出现平台名字」。**

## 二、三条结构原则

### 原则 1：能力是布尔字段，不是 `if (平台)`

```ts
// types.ts:215-226
export interface ProviderCapabilities {
  search: boolean
  playback: boolean
  lyrics: boolean
  auth: boolean
  playlists: boolean
  albums: boolean
  artists: boolean
  recommendations: boolean
  userCloud: boolean
  likes: boolean
}
```

「酷狗没有每日推荐」被表达成：

```ts
recommendations: false
```

而不是界面上判断平台名。界面统一问：

```ts
providerSupports(provider, 'recommendations')   // registry.ts:55-60
```

**为什么这件事值得单独强调**：布尔字段是**数据**，`if (平台)` 是**代码**。数据可以被注册表统一处理、可以配测试、可以在设置页列出来；代码分支只能靠人记得在每个新平台处补一遍。

### 原则 2：一首歌自带出处

```ts
// types.ts:264-266
export type PlaybackSourceRef =
  | { kind: 'online'; providerId: ProviderId; mediaId: string }
  | { kind: 'local'; mediaId: string }
```

接口 `getPlaybackSourceRef(track)`（`registry.ts:74-84`）**从歌本身**算出它属于谁，而不是靠「调用方记得它来自哪个页面」。

这条原则解决的是**混合列表**问题：一个歌单里既有本机文件又有三个平台的歌，行渲染器不需要知道平台的存在，只需要问「这行的出处是什么」。

```ts
// registry.ts:76-83
const source = track?.source
if (!track || !source || source === 'local') {
  return { kind: 'local', mediaId: track?.path ?? '' }
}
return { kind: 'online', providerId: source, mediaId: mediaIdOf(track.id, source) }
```

注意 `Track.source` 是**已经有**的字段（第 2 章的 Track 接口里有 `source?`）——这个设计的成本只是「多一个函数」，不是「改数据模型」。

### 原则 3：可用性不是错误

见第六节。这条最反直觉，也最容易做错。

## 三、`ProviderId = string`：类型宽松的三种选择

```ts
// types.ts:26-27
/** A platform's own identifier. String, not a union, so adding one costs no edits here. */
export type ProviderId = string
```

类型可以写得很严：

```ts
type ProviderId = 'netease' | 'qq' | 'kugou' | 'qishui' | 'bilibili'   // 封闭
```

也可以很松：

```ts
type ProviderId = string    // 本项目选的
```

**差别在哪？**

| 写法 | 加平台时要改什么 | 打错字会怎样 |
| --- | --- | --- |
| 封闭 union | 这个定义 + 所有 `switch` 的穷尽检查 | 编译报错（好） |
| `string` | 什么都不用改 | 编译通过，运行时查不到 provider（坏） |

本项目选 `string`，理由写在注释里：**「加一个平台不改这里」**。

这是**用它换来一个具体好处**：平台是逐个加的，每加一个都要动一次共享的类型定义，会让「改一个平台」变成「改全局」。而打错字的风险被另一个机制兜住了——`getProvider()` 返回 `null`，`sourceLabelById()` 原样返回未知 id（不谎称「本机」）。

> **这就是「类型严格度」的真实取舍**：不是越严越好，而是看「变化频率」。**变化频繁的边界，宁可用宽松类型 + 运行时兜底；稳定的内部形状，才值得用穷尽 union 锁死。**

## 四、失败词汇表：十行类型里的三个决定

### 4.1 已知的九种失败

```ts
// src/env-types/platforms.d.ts:7-17
/** Why a track cannot play. Drives the message; never collapse these into "下架". */
export type NeteaseFailureReason =
  | 'login-required'
  | 'vip-required'
  | 'region-limited'
  | 'trial-only'
  | 'taken-down'
  | 'network'
  | 'rate-limited'
  | 'service-unavailable'
  | 'unknown'
```

注释那句 **"never collapse these into 下架"** 是整张表的灵魂：**「你需要登录」「你没有会员」「你在的区域没版权」「只有试听片段」「这首歌真的没了」是五件完全不同的事。** 对用户来说它们导向五种不同的行动（登录 / 充值 / 放弃 / 接受片段 / 放弃）；如果全报「播放失败」，用户什么都做不了。

### 4.2 `string & {}`：一个必须解释的写法

```ts
// types.ts:29-38
/**
 * The union is the known set, and the `string & {}` member is the escape hatch:
 * ...
 * A closed union would make every such addition a cross-module edit; an open
 * `string` would lose the exhaustiveness that makes the wording table trustworthy.
 */
type OnlineFailureReason = NeteaseFailureReason | (string & {})
```

`string & {}` 是 TS 里的一个技巧。为什么不是直接 `| string`？

- `'a' | 'b' | string` 会**塌缩成 `string`**——编译器认为整个联合就是 string，`switch` 的穷尽性检查彻底失效，编辑器也不再提示已知值。
- `... | (string & {})` 保住了字面量提示（编辑器仍然知道九个已知值），同时允许任意字符串通过。

**它买来的是**：新平台自己发明一个 reason 时，不用改共享类型就能编译通过，`failureText` 的 `default` 分支会给一句通用文案。

**它付出的是**：编译器不再保证你处理了所有情况。

> 这就是工程上典型的**「宽松的扩展点 + 集中的兜底」**：给未来留门，但门口一定站着一个能接住任何人的兜底函数。
>
> **判据**：如果这个 union 的每个成员都是「我要为它写专属文案」的，就不能留门；如果留门时有一个可信的兜底，门就可以留。

### 4.3 一张表管所有平台

```ts
// types.ts:552-573
export function failureText(reason: OnlineFailureReason, platform = '在线平台'): string {
  switch (reason) {
    case 'login-required': return '这首歌需要登录后才能获取播放地址'
    case 'vip-required':   return '这首歌需要会员，当前账号没有权限'
    case 'region-limited': return '这首歌在你所在地区没有版权'
    case 'trial-only':     return '只能试听片段，完整版需要会员'
    case 'taken-down':     return '这首歌已下架或没有版权'
    case 'network':        return '网络请求失败，请检查连接后重试'
    case 'rate-limited':   return '请求太频繁了，稍等一下再试'
    case 'service-unavailable': return `${platform}接口暂时不可用`
    default:               return '播放失败，原因未知'
  }
}
```

三个设计点：

- **平台名由调用方传入**，所以一张表服务五个平台。不用写五份文案（五份就会渐渐不一致）。
- **每个用例的「行动建议」不同**：`rate-limited` 说「稍等一下」而不是「检查连接」——因为用户该做的事不一样。
- **`default` 是必须的**，因为 4.2 留了门。

### 4.4 什么值得重试

```ts
// types.ts:533-543
export function isTransientFailure(reason: OnlineFailureReason): boolean {
  return reason === 'network' || reason === 'rate-limited' || reason === 'service-unavailable'
}
```

九种失败被分成两类：

| 类别 | 例子 | 再问一次有意义吗 |
| --- | --- | --- |
| **终局**（this session 内确定） | `login-required` / `vip-required` / `taken-down` / `region-limited` | 没有。同一个账号、同一首歌，答案不会变 |
| **瞬时** | `network` / `rate-limited` / `service-unavailable` | 有。网络会恢复，限流会过去，后端会启动完 |

**为什么这个判断要单独抽成函数**：它决定「要不要自动重试」。重试一个 `vip-required` 是纯粹的浪费（还刷日志）；不重试一个 `network` 是让用户手动点。

注释里还有一句重要的：**未识别的原因也当作可重试**——因为「重试的成本有上限」（缓存的 TTL 兜住），猜错的代价是一次请求，不是一个死循环。

## 五、能力接口 vs 「有方法就是有能力」

看 `OnlineMusicProvider` 的后半部分（`types.ts:466-516`）：

```ts
search?: ProviderSearchApi
playback?: ProviderPlaybackApi
lyrics?: ProviderLyricsApi
auth?: ProviderAuthApi
catalog?: ProviderCatalogApi
recommendations?: ProviderRecommendationsApi
likes?: ProviderLikesApi
playlists?: ProviderPlaylistWriteApi

/** The albums this account collected. */
collectedAlbums?(): Promise<ProviderCollectedAlbum[]>
/** The artists this account follows. 同上：有方法就有这条通道。 */
followedArtists?(): Promise<ProviderFollowedArtist[]>
```

注意这些末尾的 `?`：**没实现的方法就是不存在的通道**。

这段注释记录了一次真实的踩坑：

```ts
// types.ts:480-487
/**
 * 没有这条通道的平台不定义这个方法——「有这个方法」本身就是能力声明。
 * 界面据此决定给不给入口，不再另立一张布尔表去描述同一件事（那两张表迟早会不一致，
 * 2026-11 接 QQ 关注艺人时已经踩过：接口有了、表里没这一项，页面只能硬编码平台名）。
 */
```

**教训**：如果「能不能做」有两处记录（一张布尔表 + 一个方法），它们**早晚会不一致**，而不一致的表现就是「功能实现了但界面不给入口，只好硬编码平台名」。

**规则**：**一件事只在一处声明。** 有方法就有能力；`capabilities` 那十个布尔只用于「界面上的一级入口要不要出现」这种粗粒度判断。

> 顺带看 `backend?: unknown`（`types.ts:516`）——那是**给 store 调用的**，和给界面调用的能力接口刻意分开。注释说得很明白：provider 可以声明能力、但 store 仍然可以拒绝驱动它。**「界面能问什么」和「状态机真的会调什么」是两个问题**，混在一起就是两处不一致。

## 六、可用性三态：最反直觉的一节

```ts
// types.ts:268-269
type SongAvailabilityState = 'playable' | 'unavailable' | 'unknown'
type SongUnavailableReason = 'taken-down' | 'restricted'
```

再看它的规则（`types.ts:271-291`）：

> `state 'unavailable'` **only ever** pairs with `'taken-down'`. Permission, payment and region limits are `state 'unknown'` + `reason 'restricted'`, left for the runtime to decide. **A runtime failure is never written back here.**

翻译成一句话：**「没了」和「你放不了」是两回事，绝不能混。**

具体例子：

```ts
// types.ts:282-285
// QQ's VIP tracks (upstream `result=104003`) are `unknown` / `restricted`,
// **not** `unavailable`, and not an error.
```

为什么这件事这么重要？因为**一个 VIP 歌标成「已下架」的后果是永久的**：

- 缓存里存成「下架」→ 用户充了会员还是放不了，因为代码不再去问了；
- 列表里显示「已下架」→ 用户以为平台没这首歌，实际是自己没权限。

**正确的表达是「我不知道你能不能放，去问运行时」**。而运行时的答案（成功 / `vip-required`）**不写回可用性状态**——因为它只对这一次、这个账号成立。

> 这个模式可以推广到任何「本地缓存的判断」：**缓存「确定的事实」，不缓存「此刻的结果」。** 文件不存在是事实；HTTP 403 是此刻的结果。

对比一下常见做法：

```ts
// 常见但错的做法
if (fee !== 0) availability = 'unavailable'    // 把「要收费」当「没了」
```

短期没问题，长期就是「充了会员还能看到『已下架』」这种诡异 bug。

## 七、音质：八档、短名、只报告不重试

```ts
// types.ts:44-53
const QUALITY_TIERS: QualityTier[] = [
  'standard', 'higher', 'exhigh', 'lossless',
  'hires', 'jyeffect', 'sky', 'jymaster'
]
```

按「从差到好」排序。注释说明 `jyeffect`/`sky`/`jymaster` 是网易云在无损之上的三档（高清环绕 / 沉浸环绕 / 超清母带）。

**为什么要有序**：因为有 `qualityRank()`（`types.ts:523-526`）——判断「实际拿到的档位是不是低于请求的档位」必须能比较大小。

```ts
// types.ts:528-531
/** Whether what arrived is below what was asked for. Reported, never retried. */
export function isQualityFallback(level: QualityTier | 'hires', requested: QualityTier): boolean {
  return qualityRank(level) < qualityRank(requested)
}
```

**"Reported, never retried"** 是一个重要的产品决定：平台没给你母带，重试一百次还是没有。**如实报告「低于所选」比假装拿到了更重要**——用户有权知道自己在听什么。

### 中文短名：一个 30px 的约束

```ts
// types.ts:55-70
/**
 * 「超清母带」四个字放进 30px 高的播放条里会被挤成两行，整条播放条跟着错位——
 * 这一列只做一件事：让它一个字都不换行。菜单里仍然是全名。
 */
export const QUALITY_SHORT: Record<QualityTier, string> = {
  standard: '标准', higher: '较高', exhigh: '极高', lossless: '无损',
  hires: 'Hi-Res', jyeffect: '环绕', sky: '沉浸', jymaster: '母带'
}
```

这里有个**可以学一辈子的细节**：同一件事在不同地方需要不同长度。播放条上一个字都不能换行，菜单里可以写全名。于是有 `QUALITY_SHORT` 与 `QUALITY_LABELS` 两张表。

**不要为了「统一」把两处合成一张。** 它们的约束不同（一个是 30px 高度，一个是完整说明），合并会让其中一处必然将就。

### 会员档位的判断

```ts
// types.ts:495-501
/**
 * 这些档位需要会员。账号明确是「非会员」时，界面把它们藏起来。
 * 只声明「确定要会员」的档；没声明的档一律对所有账号开放——宁可多显示一个
 * 拿不到的档（会自动降级并如实报告），也不要在不确定时藏掉一个能用的。
 */
qualityNeedsVip?: QualityTier[]
```

**注意这个方向的偏向**：不确定时**显示**而不是隐藏。

为什么？因为隐藏的代价是「用户不知道有这回事」，显示的代价是「点了会降级」。前者用户永远发现不了，后者用户立刻看到提示（`streamSummary` 会写「低于所选」）。**不确定时的默认值，应该偏向「用户能看见并自己判断」。**

## 八、非登录状态要说实话

```ts
// types.ts:441-454
/**
 * What actually works without signing in, in the platform's own words.
 *
 * A field rather than one shared sentence, because the platforms genuinely
 * differ and the shared sentence was wrong for one of them: Netease plays free
 * tracks in full and hands out trial fragments of paid ones, while QQ was
 * measured at only 18.4% playable signed out (free tracks, 128 kbps) - every
 * `payplay === 1` track answers `result=104003`. The screen used to tell both
 * platforms "searching and playback need no sign-in", which for QQ described a
 * catalogue where most clicks do nothing.
 */
anonymousNote: string
```

这一段是**整个文件里最有价值的一课**，因为它记录了一次「统一的文案说了谎」：

- 界面原本对两个平台都说「搜索和播放无需登录」；
- 网易云：这句话是对的（免费歌能放全文，付费歌给试听片段）；
- QQ：**实测只有 18.4% 的歌能在未登录下播放**，`payplay === 1` 的全部返回 `104003`。

于是**同一句话对一个平台是准确的，对另一个是误导**——而用户会为此浪费大量点击。

**结论不是「删掉那句话」，而是「把它变成一个每个平台必须自己填的字段」**：

```ts
provider.anonymousNote   // 各平台自己写
```

> 这可以推广成一条设计规则：**当一句共享文案无法对所有对象都成立时，把文案变成对象的一个必填字段。** 字段是诚实的，共享常量是懒惰的。

## 九、注册表：一张 Map 和三个决定

`registry.ts` 只有一种数据结构：

```ts
const providers = new Map<ProviderId, OnlineMusicProvider>()
```

### 决定 1：注册顺序 = 显示顺序

```ts
// registry.ts:22-31
/**
 * Registration order is display order.
 * Netease first because it has been here longest, and because the order is used
 * verbatim by the rail and the search tabs - a stable order matters more than an
 * alphabetical one when the list is navigation.
 */
```

**导航顺序要稳定，不要「更美观」。** 用户按位置记忆入口；今天按字母排、明天按热度排，等于每天都在重新学习。

### 决定 2：`listProviders` 与 `listAvailableProviders` 是两个问题

```ts
// registry.ts:37-53
/**
 * Not filtered by `available()`: a caller that wants "what can I offer the user"
 * asks for `listAvailableProviders()`, and a caller that wants "what exists"
 * (the settings page lists tiers for platforms the app supports) gets the full set.
 * Collapsing the two is how a disabled platform becomes invisible in a screen
 * that should still explain it.
 */
export function listProviders(): OnlineMusicProvider[] { return [...providers.values()] }
export function listAvailableProviders(): OnlineMusicProvider[] {
  return listProviders().filter((provider) => provider.available())
}
```

「哪些平台存在」和「哪些平台此刻能用」是两个问题。设置页要知道全部（否则用户看不到「QQ 需要登录后端」），来源页只要可用的。

**用一个函数强行合并，就会让其中一类调用方拿到错的数据。** 这是 API 设计里最常见的偷懒。

### 决定 3：`available()` 每次渲染都重新问

```ts
// types.ts:456-464
/**
 * False when this build has no backend for the platform at all ...
 * Read at render time, never cached: the interface must not offer an entry for
 * a platform it cannot serve, and the answer can change when the app is
 * rebuilt or the backend finishes booting.
 */
available(): boolean
```

**不要缓存**。后端可能在启动几秒后才就绪；开发时的构建也可能根本没有某个平台的后端。「这个平台能用吗」是个**会被时间改变的问题**，缓存答案就是缓存了一个过期的判断。

## 十、混合列表的标签：`listIsMixed`

```ts
// registry.ts:110-130
/**
 * `listIsMixed` is what keeps the label honest instead of noisy. A screen that
 * speaks with one voice - only files (the songs page, an album), or only one
 * platform's songs (that platform's own list) - never prints anything, because
 * the page title and the "结果来自" line already answer it. A screen that mixes
 * origins (a playlist, the queue) prints one on every row, including the files.
 */
```

`sourceTagFor(track, listIsMixed)` 的逻辑很简单：**只有混合列表才打标签**。

- 纯本机列表（专辑页）：每一行都写「本机」是噪音，页面标题已经说了；
- 纯某平台列表（网易云页）：每行都写「网易云」也是噪音；
- 歌单 / 播放队列：必须写，否则用户不知道哪首歌放不了。

**「什么时候不该显示信息」和「显示什么信息」一样重要。** 每个列表页都堆来源标签的结果是用户学会无视它。

## 十一、接入一个新平台：检查清单

按这个顺序，前四步都在 `electron/` 里，第五步才碰界面：

| 步骤 | 做什么 | 常见错误 |
| --- | --- | --- |
| 1 | 写 `electron/<platform>/` 客户端，输出**归一化**的形状 | 把上游字段（`songmid`、`albumname`）泄漏到共享类型 |
| 2 | 在 `src/env-types/platforms.d.ts` 声明类型面 | 新造一套失败原因（应该复用 `NeteaseFailureReason`） |
| 3 | IPC 通道 + preload 暴露 | 忘了 preload（界面拿不到、也不报错） |
| 4 | 实现 `OnlineMusicProvider`：`capabilities` 老实填、可选方法按需给 | 能力表填了 `true` 但方法没实现 |
| 5 | `registerProvider()` 一次 | 忘了注册（注册表里没有 = 界面看不见） |
| 6 | 设置页 `/ 来源页` 自动出现（不用改界面） | 如果必须改界面，说明前面某步泄漏了平台名 |

**判据**：**如果第 6 步需要改界面代码，说明契约被破坏了。** 这是整个第 4 章最好的验收标准。

## 十二、把这一篇收成清单

| 问题 | 答案 |
| --- | --- |
| 多平台接入的真正难点是什么？ | 界面里长出 `if (平台)`，接到第五个就没人记得补 |
| 能力为什么用布尔字段？ | 数据可集中处理、可测试；代码分支只能靠人记 |
| 歌为什么要自带出处？ | 混合列表的行不需要知道平台存在 |
| `ProviderId = string` 图什么？ | 加平台不改共享类型；错误由运行时兜底 |
| 失败原因为什么不能合并成「失败」？ | 九种原因导向九种用户行动 |
| `string & {}` 是什么？ | 保住已知值提示 + 允许扩展；代价是丢穷尽检查 |
| 什么值得重试？ | 只有 `network` / `rate-limited` / `service-unavailable` |
| VIP 歌能标「已下架」吗？ | 绝不能。是 `unknown` + `restricted`，交给运行时 |
| 运行时失败要写回可用性吗？ | 不。缓存事实，不缓存此刻的结果 |
| 为什么有短名和全名两张表？ | 30px 的播放条不能换行，菜单要完整说明 |
| 不确定会员档位时怎么办？ | 显示（偏向用户能看见），自动降级并如实报告 |
| QQ 匿名能播多少？ | 实测 18.4%（免费歌，128kbps），`payplay===1` 全返回 `104003` |
| 为什么匿名说明要变成字段？ | 一句共享文案无法同时对网易云和 QQ 成立 |
| 注册顺序为什么就是显示顺序？ | 导航按位置记忆，稳定比「更优」重要 |
| `listProviders` 为什么不按可用性过滤？ | 设置页要能看到不可用平台并解释原因 |
| `available()` 能缓存吗？ | 不能，后端启动后答案会变 |

## 十三、延伸阅读

- **TypeScript Handbook · Narrowing**：`(string & {})` 这个技巧的原理就在这里（字面量类型、可辨识联合、穷尽性检查）。
- **TypeScript Handbook · Discriminated Unions**：`PlaybackSourceRef` 的 `kind` 字段就是标准做法。
- **项目内** `docs/other-players-platform-adapters.md`（45 KB）：记录了其他播放器怎么处理多平台、以及本项目的取舍。这是「对标与反驳」的最好材料。
- **项目内** `docs/architecture.md` 的在线平台一节：模块地图与调用链。
- **MDN · HTTP 状态码**：`isTransientFailure` 的直觉来自 HTTP —— 4xx 是「你的问题」（别重试），5xx 是「服务器的问题」（可以重试）。
- **项目内** `README.md` 的「关于在线平台」一节：法务与诚实披露的写法。

**建议的动手**：给 `failureText` 加第十种 reason（比如 `'need-purchase'`），走一遍「改一处 → 编译 → 界面显示」的链路。你会发现**真的只改了一处**——这就是这 800 行存在的意义。
