# 文献 2 · 私有协议与缓存：页面怎么安全地读到文件

> **读这篇之前**：读完第 4 站（Node 与 Electron）的 preload 与 IPC 部分。
> **读完之后**：你应该能自己写一个最小的 `aurora-xxx:` 协议，并且能解释「为什么缓存不放在远程代理里面」。

本篇以 `electron/protocols/` 下四个文件（`app` / `media` / `remote` / `cache`）为教材。
**它们是这个项目里「安全」与「性能」两条线交汇的地方**，也是最容易出静默 bug 的地方。

---

## 一、问题的起点：页面为什么不能直接读文件

Electron 里页面跑在 Chromium 里。它默认只能：

- 用 `fetch` 请求 http/https 地址；
- 用 `<img>`/`<audio>` 加载 http/https 资源。

它**不能**：

- 读 `D:\Music\某首歌.flac`；
- 读打包进 `app.asar` 的前端资源；
- 让 `<audio>` 走 Web Audio（跨源会静音，见文献 1）。

而 Aurora 三件事都要做。于是有了私有协议——**给「本机资源」造一个 URL scheme，让页面能用正常 Web 的方式访问它。**

```
页面的视角                主进程的视角
aurora-media://audio/...  ──►  fs.createReadStream('D:/Music/x.flac')
```

**这就是全部意义**：不是「新功能」，是**把已有能力包装成 Web 认识的形状**。

---

## 二、五种 scheme，五个用途

| scheme | 服务什么 | 文件 |
| --- | --- | --- |
| `aurora-app:` | 打包后的前端资源（HTML/JS/CSS/字体） | `app-protocol.ts` |
| `aurora-media:` | 本地音乐文件（支持 Range，能拖进度） | `media-protocol.ts` |
| `aurora-remote:` | 在线音频的代理（解决 CORS，透传 Range） | `remote-protocol.ts` |
| `aurora-cache:` | 在线音频的**缓存层**（命中读本地，未命中透传并回填） | `cache-protocol.ts` |
| `aurora-wallpaper:` | 壁纸资源（`wallpaper.ts`） | `wallpaper.ts` |

**为什么不是一个 scheme 带不同 host？** 因为它们的**信任等级不同**：
`aurora-app:` 只读打包目录，`aurora-media:` 只读用户授权的音乐目录，`aurora-remote:` 能发网络请求，`aurora-cache:` 两者都碰。**分开注册，权限边界才清晰**——一个 scheme 出漏洞，不至于把所有能力一起暴露。

---

## 三、协议的两段式生命周期（最容易错的地方）

把协议看成「注册一个 URL 前缀」，新人最常犯的错是**注册时机**。

```ts
// cache-protocol.ts:204-223
export function registerCacheScheme(): void {
  const { protocol } = electronProtocol()
  protocol.registerSchemesAsPrivileged([{ scheme: CACHE_SCHEME, privileges: {...} }])
}

export function handleCacheProtocol(cache: MediaCache): void {
  const { protocol } = electronProtocol()
  protocol.handle(CACHE_SCHEME, (request) => handleCacheRequest(request, cache))
}
```

两个函数，对应两个**必须分开**的阶段：

| 阶段 | 时机 | 干什么 |
| --- | --- | --- |
| `registerSchemesAsPrivileged` | **`app.ready` 之前** | 告诉 Chromium「这个 scheme 有什么特权」，属于配置 |
| `protocol.handle` | **`app.ready` 之后** | 挂上「收到请求怎么办」的处理函数 |

**为什么不能合并**：`registerSchemesAsPrivileged` 影响的是 Chromium **启动时**的进程配置（安全源、是否走 standard URL 解析、能否 fetch）。等 `app.ready` 再调，Chromium 已经初始化完了，**调用会静默无效**——页面加载时表现为「资源 404 / CSP 拒绝」，而你找不到原因。

> 这是本项目里唯一一类「改错了不报错」的错误。**加新协议时，先把注册函数放到 `main.ts` 的 `whenReady` 之前。**

## 四、privileges 五个开关逐个解释

```ts
privileges: {
  standard: true,
  secure: true,
  supportFetchAPI: true,
  stream: true,
  corsEnabled: true
}
```

| 开关 | 含义 | 关掉会怎样 |
| --- | --- | --- |
| `standard` | 按 URL 标准解析（有 host/path、相对路径可用、URL 对象完整） | `new URL()` 出来的 host/path 不可靠，相对路径解析废掉 |
| `secure` | 视作安全源（等同 https） | 页面认为它不安全，某些 API 拒绝在非安全上下文工作 |
| `supportFetchAPI` | 允许 `fetch('aurora-cache://...')` | 只能当资源用（`<img src>`），不能用 `fetch` 读内容 |
| `stream` | 支持流式响应与 Range | **不能拖进度条**（原注释：`stream: true` is what allows range requests, and therefore seeking） |
| `corsEnabled` | 参与 CORS 检查（配合响应头） | 跨源请求被直接拒绝，Web Audio 静音 |

**这五项基本是「音频类协议的最小完整集」**。写新协议时照抄这五个，然后按需删减——但删之前要清楚自己删掉了什么能力。

## 五、为什么缓存要单独一个 scheme

这是整个设计里最漂亮的一步。原文注释（`cache-protocol.ts:7-21`）：

> Why a second scheme instead of caching inside the remote proxy: the remote URL is a signed CDN address that changes between plays, so it cannot be the cache key. The renderer knows which provider and track it is asking for, and puts that identity in the URL; the upstream address rides along as the fallback for the first play. From then on the upstream part is never needed, which is what makes the "no network on the second play" acceptance test possible.

拆解：

1. **在线音频地址是带签名的**，每次播放都不一样 → **不能拿它当缓存 key**。
2. 但渲染层知道「这是哪个平台的哪首歌」——`netease:12345` 这种身份是稳定的。
3. 所以 URL 设计成：

   ```
   aurora-cache://audio/<稳定 key>/<百分号编码的上游地址>
   ```

4. 第一次播放：上游地址有用（去拿）。**第二次播放：主进程按 key 命中缓存，整个请求根本不出机器。**

注释里那句 acceptance test 是关键：**「第二次播放时不需要网络」是可以被验收的**——拔网线再放同一首歌，还能出声。这就是为什么设计要这么绕。

**通用经验**：缓存 key 必须是**稳定的业务身份**，不能是「获取它的地址」。这个原则在大到 CDN、小到一个 `Map` 缓存里都成立。

## 六、URL 解析：一行注释藏着一个坑

```ts
// cache-protocol.ts:53-58
// The key is encoded as a single segment, and it contains a colon
// (`netease:12345`), which `encodeURIComponent` leaves alone - safe in a path
// segment and readable in a log line.
```

`encodeURIComponent('netease:12345')` 的结果是 `netease%3A12345`？**不是**——`encodeURIComponent` 不会编码 `:`、`/` 之外的 `!'()*-._~` 和字母数字。**冒号保留原样。**

于是 key 里带着冒号出现在 URL path 里，仍然可读（日志里一眼看出是哪首歌）。如果靠 `%3A`，日志里全是百分号，排错会痛苦。

**但要注意**：如果是 `encodeURI` 而不是 `encodeURIComponent`，`/` 也不会被编码，key 里一旦有斜杠，整个路径解析就错位了。**URL 里放数据，永远用 `encodeURIComponent` 而不是 `encodeURI`。**

## 七、Range 请求：拖进度条背后的协议

`<audio>` 拖进度条时，浏览器不会重新下载整个文件，而是发：

```
Range: bytes=1048576-2097151
```

服务器应该回：

```
206 Partial Content
Content-Range: bytes 1048576-2097151/4194304
Content-Length: 1048576
```

`cachedAudioResponse`（`cache-protocol.ts:82-109`）逐条实现了：

```ts
const range = parseRange(request.headers.get('range'), entry.size)
if (range === 'invalid') {
  headers.set('content-range', `bytes */${entry.size}`)
  return new Response(null, { status: 416, headers })     // 越界
}
const start = range ? range.start : 0
const end = range ? range.end : entry.size - 1
headers.set('content-length', String(end - start + 1))
if (range) headers.set('content-range', `bytes ${start}-${end}/${entry.size}`)
const status = range ? 206 : 200
if (request.method === 'HEAD') return new Response(null, { status, headers })
const body = Readable.toWeb(fs.createReadStream(entry.path, { start, end }))
```

四个必须做对的点：

1. **`206` 而不是 `200`**：状态码错了，浏览器会认为「不认 Range」，退化成整文件下载。
2. **`Content-Range` 的格式**：`bytes start-end/total`，**总长必须有**，否则浏览器算不出还剩多少。
3. **`416` + `Content-Range: bytes */total`**：请求越界时这么回。`*/` 是特殊语法，只在这一处用。
4. **`HEAD` 不能带 body**：只回头，不返内容。

还有一个容易漏的：

```ts
// cache-protocol.ts:76-79
function rangeHeaders(headers: Headers): void {
  headers.set('accept-ranges', 'bytes')
  headers.set('access-control-expose-headers', 'content-range, content-length, accept-ranges')
}
```

`access-control-expose-headers` 为什么必要？**跨源响应里，JS 默认只能读六个「安全头」**（`content-type` 之类），其他头（包括 `content-range`、`accept-ranges`）对 JS 不可见——**除非显式暴露**。不写这一行，前端的媒体库读不到总长，进度条算不出来。

**这是个纯粹的 Web 平台细节，但它是「能拖」和「不能拖」的分界。**

## 八、`no-store`：让「清缓存」真的清得掉

```ts
// cache-protocol.ts:85-90
/*
 * The file is a cache the app manages; letting Chromium keep a second copy in
 * its HTTP cache would make "clear cache" leave bytes behind.
 */
headers.set('cache-control', 'no-store')
```

简单而深刻：**应用自己的缓存层，不该再叠一层浏览器缓存**。否则用户点了「清理缓存」，磁盘上还留着 Chromium 那一份，下次播放还是不出网络——用户会觉得「这个按钮是假的」。

**通用原则**：凡是「应用自己管生命周期」的资源，都要关掉下层的自动缓存。

## 九、回填缓存：为什么是第二个请求

```ts
// cache-protocol.ts:111-119
/**
 * Fill the cache in the background while the current play streams from upstream.
 *
 * Deliberately a second request rather than a tee of the one the player is
 * reading: a tee dies with the first play-through (the user skips to the next
 * track at 0:30 and the download is cancelled with it), and the byte ranges a
 * player requests are not the whole file anyway. One extra request on the first
 * play buys a cache that is always a complete file.
 */
```

「tee」是流处理里的概念：一个源分成两路，一路给播放器、一路写文件。看似省一次请求，实际有两个致命问题：

1. **tee 的生命周期绑在播放上**：用户 0:30 切歌，播放中断 → 写文件也中断 → 缓存里躺着一个**残缺文件**。
2. **播放器不会请求整个文件**：它按 Range 一段段要，tee 出来的永远是断断续续的片段。

所以：**另起一个完整请求去下载**。代价是多一次请求（还只在首次播放），换来「缓存里永远是完整文件」。

**这是一个「正确性 vs 一点点带宽」的取舍，而且选择了正确性。**

同时它还有一整套防御：

```ts
if (pending.has(key)) return          // 同一首并发播放，只下一次
if (!response.ok || !response.body) return
const type = (response.headers.get('content-type') ?? '')...
if (type && !type.startsWith('audio/') && type !== 'application/octet-stream' && ...) return
await cache.store(key, ...)
} catch { /* a background cache fill must never surface as a playback failure */ }
```

三个要点：

- **`pending` Map**：用户连点两下播放，不能起两个下载。
- **内容类型检查**：CDN 有时回 `application/octet-stream` 或 `binary/octet-stream`（注释说「前几个字节到底还是能判断的」），所以只拒绝「确定不是音频」的。
- **`catch` 吞掉异常**：**后台回填失败不能变成播放失败**。这句注释是整个缓存设计的底线——缓存是优化，不是依赖。

## 十、主流程：命中、鉴权、代理

```ts
// cache-protocol.ts:164-202（精简）
if (request.method === 'OPTIONS') return new Response(null, { status: 204, headers: PREFLIGHT_HEADERS })
if (request.method !== 'GET' && request.method !== 'HEAD') return 405
const target = parseCacheTarget(url) ?? return 400

const hit = await cache.lookup(target.key)
if (hit) return cachedAudioResponse(hit, request)      // 命中：不出机器

if (!(await isAllowedHost(hostname))) return 403        // 未命中：先鉴权
fillCache(cache, target.key, target.upstream)           // 后台回填
return await proxyUpstream(...)                        // 同时透传给播放器
```

**顺序值得记**：命中检查在**鉴权之前**。

```ts
// cache-protocol.ts:180
// A hit never leaves the machine: no DNS check, no upstream request at all.
```

这不是漏洞，是刻意的：命中路径根本不发网络请求，也就不需要「允许访问哪些主机」的判断。**只对真正出网的路径做安全检查**——这条原则让热路径保持极快。

### OPTIONS 预检

跨源 `fetch` 带自定义头（比如 `Range`）时，浏览器先发一个 `OPTIONS` 预检，问「我可以这么做吗」。`PREFLIGHT_HEADERS`（第 39-45 行）回答了这个许可：

```
access-control-allow-methods: GET, HEAD, OPTIONS
access-control-allow-headers: range
access-control-expose-headers: content-range, content-length, accept-ranges
access-control-max-age: 600
```

`max-age: 600` = 十分钟内不用再问。**少了这一段，跨源请求会在预检阶段就失败，而且错误信息通常只说「CORS 失败」，很难定位。**

### 透传头白名单

```ts
const PASSTHROUGH = ['content-type', 'content-length', 'content-range', 'etag', 'last-modified']
```

为什么不把所有头都透传？因为上游的 `set-cookie`、`content-encoding`、各种 CDN 私有头，透给页面要么没用、要么有害（`content-encoding` 会让浏览器二次解压）。**白名单比黑名单安全**——这是协议层通用的经验。

另外：

```ts
if (!headers.has('content-type')) headers.set('content-type', 'audio/mpeg')
```

**缺省 MIME 要给一个合理的**。没有 content-type，某些浏览器会拒绝把响应当音频解码。

## 十一、安全：`isAllowedHost` 在防什么

```ts
// remote-protocol.ts:173-191
if (host === 'localhost' || host.endsWith('.localhost')) return false
...
if (net.isIP(host)) allowed = !isPrivateAddress(host)
else {
  // A public name that resolves to a private address is still a private
  // address; checking the literal alone would only catch the naive case.
  const addresses = await dns.promises.lookup(host, { all: true })
  allowed = addresses.every((entry) => !isPrivateAddress(entry.address))
}
```

**这防的是 SSRF**（Server-Side Request Forgery，服务端请求伪造）：攻击者让应用去请求 `http://192.168.1.1/admin`，借应用的网络位置访问内网。

只检查字面量地址是不够的——**域名可以解析到内网 IP**（DNS rebinding / 恶意 DNS）。所以必须：

1. 先解析域名（`dns.lookup(host, { all: true })`，**要全部结果**）；
2. 检查每一个解析结果都不是私有地址；
3. 任何一步失败或超时 → 拒绝（`catch { allowed = false }`）。

**「失败时默认拒绝」**（fail closed）是安全代码的铁律。反过来（失败时放行）叫 fail open，是漏洞的常见来源。

最后一句也值得学：

```ts
// cache-protocol.ts:198
// The URL carries a signature; only the host goes into the log.
console.error('[aurora] cached stream fallback failed', hostname, error)
```

**日志里不能出现带签名的完整 URL**——URL 里的签名参数等于凭据，写进用户日志、被贴到 issue 里，就是泄露。**只记 host。**

## 十二、`handleCacheRequest` 为什么要独立

```ts
// cache-protocol.ts:160-163
/**
 * One request, decoupled from the scheme registration so a probe or a test can
 * drive it directly.
 */
async function handleCacheRequest(request: Request, cache: MediaCache): Promise<Response>
```

它接收一个标准的 `Request`，返回标准的 `Response`，**不碰 `protocol` 对象**。于是：

```ts
// 测试里可以直接这样
const res = await handleCacheRequest(new Request('aurora-cache://audio/k/...'), fakeCache)
```

**这是「把副作用推到边缘」的又一例**：真正难测的是「Electron 什么时候调用这个函数」，好测的是「收到这个请求，该回什么」。**把两者分开，中间那条缝就是测试的入口。**

注意文件顶部还有一句解释为什么要延迟 `require('electron')`：

> Electron is required lazily and only in `handleCacheProtocol`, for the same reason `remote-protocol.ts` does it: a plain Node test process must be able to import `handleCacheRequest` without an Electron runtime.

**静态 import `electron` 会让整个文件在裸 Node 里无法加载**——一个 `import` 就能毁掉一个测试文件的可测性。所以 Electron 相关的 import 全部推迟到真正需要的那一刻。

## 十三、另一侧：页面能碰到的到底是什么

到这里，资源通路已经打通。但「页面为什么会老实走这条路，而不是直接 `require('fs')`」是另一个问题。

答案是三层安全设置（`electron/main.ts:371-380`）：

```ts
webPreferences: {
  preload,
  contextIsolation: true,      // 页面代码和 preload 不共享全局对象
  nodeIntegration: false,      // 页面不能直接用 Node
  sandbox: true,               // 渲染进程受系统级限制
  ...
}
```

逐个说清后果：

| 设置 | 如果反过来 | 后果 |
| --- | --- | --- |
| `nodeIntegration: false` | `true` | 页面里任何一行 JS 都能 `require('child_process').exec()`。**一个 XSS = 完全控制机器。** |
| `contextIsolation: true` | `false` | preload 暴露的对象和页面共享原型链，页面可以篡改 preload 里的函数（原型污染） |
| `sandbox: true` | `false` | 渲染进程能做的系统调用更多，漏洞影响面更大 |

**这三条是 Electron 安全的底线，不是可选项。** 项目里所有「页面需要原生能力」的地方，都必须经过：

```
页面 → src/bridge.ts → window.aurora → preload 的 contextBridge → ipcRenderer.invoke → 主进程
```

`preload.ts` 里 `contextBridge.exposeInMainWorld('aurora', api)` 那一步，是**唯一合法的出口**。它能暴露的每个方法，都是**有意的授权**。

### CSP 是最后一道

`index.html` 里的 CSP 决定页面**允许加载哪些前缀**的资源：

```
img-src 'self' aurora-app: aurora-media: aura-cache: data:;
media-src aurora-media: aurora-cache: aurora-remote:;
connect-src 'self' aurora-cache: aurora-remote:;
```

**加了新 scheme，不往这里加，页面就是拿不到——而且控制台只报一句「违反 CSP」。**
这是第 4 站和第 7 章反复强调「四处同步」的原因：协议注册、handler 挂载、CSP 放行，缺一处都是静默失败。

## 十四、路径穿越：`app-protocol` 里的那个函数

`aurora-app:` 服务打包目录。请求路径来自 URL，**URL 是用户可控的**（页面里可以直接 `fetch('aurora-app://app/../../../etc/passwd')`）。

所以必须有一个纯函数来裁决：

```ts
// electron/pure/app-paths.ts:36
export function resolveAppAsset(root: string, requestPath: string): string | null
```

两步检查（这个文件只有 36 行，值得全文读）：

1. **NUL 字节检查**：`%00` 解码后会出现 `\0`，某些系统调用会在 `\0` 处截断字符串——经典漏洞。
2. **解析后前缀检查**：`path.resolve(root, requestPath)` 之后，结果必须以 `root + path.sep` 开头。**光比较字符串前缀不够**（`/app-evil` 也以 `/app` 开头），要带分隔符。

返回 `null` 表示拒绝。**调用方必须把 `null` 当 404，绝不能当「就用原路径」。**

**这个函数被拆到 `pure/` 正是为了能被单独测**：它是安全边界，必须有测试钉住越界、NUL、绝对路径、符号链接这些情况。

## 十五、把这一篇收成清单

| 问题 | 答案 |
| --- | --- |
| 私有协议解决什么？ | 让页面用 Web 方式访问本机资源，绕过「不能读文件」和「跨源静音」 |
| 协议注册分几步？ | 两步：ready 前 `registerSchemesAsPrivileged`，ready 后 `protocol.handle` |
| 少了 `stream: true` 会怎样？ | 不能拖进度条 |
| 缓存 key 为什么不能用上游 URL？ | 签名地址每次都变，不稳定 |
| 缓存里躺的可能是残缺文件吗？ | 不会，因为回填是独立的完整请求，不是 tee |
| 回填失败会影响播放吗？ | 不会，`catch` 吞掉——缓存是优化不是依赖 |
| 命中缓存要鉴权吗？ | 不用，命中根本不出网 |
| `isAllowedHost` 防什么？ | SSRF：域名解析到内网 IP 也要挡住，失败默认拒绝 |
| 日志里为什么不能有完整上游 URL？ | 带签名 = 凭据，会泄露 |
| 为什么 `handleCacheRequest` 不碰 `protocol`？ | 解耦后可被测试/探针直接调用 |
| `nodeIntegration` 能开吗？ | 永远不能。一个 XSS 就能拿到整台机器 |
| 加新协议要改几处？ | 注册函数、handler、CSP 白名单（**三处**，缺一是静默失败） |

- **MDN · HTTP Range requests**：`206` / `416` / `Content-Range` 的权威说明，本篇第七节的规范来源。
