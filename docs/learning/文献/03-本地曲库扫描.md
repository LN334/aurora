# 文献 3 · 本地曲库扫描：把一台机器的硬盘变成列表

> **读这篇之前**：读完第 2 站（async/await 与闭包）和第 4 站（Node 文件模块）。
> **读完之后**：你应该能解释「为什么扫描要 8 个 worker 抢任务」，以及「为什么文件身份不能用路径字符串直接当 id」。

本篇以 `electron/library-scan.ts`（440 行）为教材。它是这个项目里**最典型的「批处理」代码**：不可信输入、长耗时、要能中断、要能增量、要能报进度。

---

## 一、先把问题定义清楚

「扫描本地音乐库」听起来是个小功能，其实它是五个问题的集合：

| 问题 | 难点 |
| --- | --- |
| **发现**：哪些文件算音乐？ | 目录结构不可预测，可能有几万个文件、有软链接、有权限拒绝的目录 |
| **读取**：每个文件的元数据怎么拿？ | 解析音频容器，慢，而且标签可能乱写（null、数组、`"-1"`） |
| **身份**：同一个文件两次扫描怎么认出来？ | 路径可能变（移动/改名），大小写不敏感 |
| **增量**：第二次扫描怎么不重做一遍？ | 得有「便宜且可靠」的变更判据 |
| **反馈**：用户要看进度、要能取消 | 进度是 UI 关注点，但扫描在主进程 |

**这五个问题，每个都对应一段独立的代码，而且几乎都是纯逻辑。** 这就是为什么这个文件看起来长，读起来却很清楚。

## 二、遍历：为什么用队列而不是递归

```ts
// library-scan.ts:114-146
async function collectAudioFiles(root: string, onFound: (file: string) => void): Promise<string[]> {
  const found: string[] = []
  const queue: string[] = [root]

  while (queue.length > 0) {
    const directory = queue.pop()
    ...
    entries = await fs.promises.readdir(directory, { withFileTypes: true })
    ...
    for (const entry of entries) {
      const full = path.join(directory, entry.name)
      if (entry.isDirectory()) {
        if (SKIP_DIRECTORIES.has(entry.name.toLowerCase())) continue
        if (entry.name.startsWith('.')) continue
        queue.push(full)
      } else if (entry.isFile()) {
        if (!AUDIO_EXTENSIONS.has(path.extname(entry.name).toLowerCase())) continue
        found.push(full)
        onFound(full)
      }
    }
  }
  return found
}
```

四个值得学的决定：

**1. 显式队列代替递归**

递归写法更短：

```ts
async function walk(dir) {
  for (const e of await readdir(dir)) {
    if (e.isDirectory()) await walk(join(dir, e.name))
    ...
  }
}
```

但递归的深度 = 目录深度，而且**每次递归都要 await**，一个目录读慢了就卡住整条链。队列写法把「待处理目录」变成数据（数组），**可以随时暂停、计数、加并发、换顺序**。

> 一句通用经验：**能变成数据的东西，就不要变成调用栈。**

**2. `pop()` 而不是 `shift()`**

`shift()` 是 O(n)（要挪动整个数组），`pop()` 是 O(1)。几万个目录时差别明显。代价是**遍历顺序变成「深度优先但逆序」**——对扫描来说顺序无所谓，所以选快的。

**3. 一个目录读不动，不能拖垮整个库**

```ts
} catch {
  // Permission denied, a dead symlink, a drive that went away: skip it and
  // keep scanning. One unreadable folder must not abort the whole library.
  continue
}
```

这是**「部分成功优于整体失败」**。扫描 2 万首歌，有 3 个目录需要管理员权限——正确行为是「扫出来 19997 首 + 3 个跳过」，不是「报错，一首都没有」。

**4. 三道过滤，顺序有讲究**

```ts
SKIP_DIRECTORIES.has(entry.name.toLowerCase())   // 系统目录、回收站…
entry.name.startsWith('.')                       // 隐藏目录
AUDIO_EXTENSIONS.has(path.extname(entry.name).toLowerCase())
```

`toLowerCase()` 出现两次：Windows 文件系统不区分大小写，但字符串比较区分。**不统一大小写，`.MP3` 会被当成非音频。**

**跳过目录的判断在 `isDirectory()` 分支里**——也就是说，**永远不会进入**这些目录，连它们下面有什么都不看。这是性能上最重要的一步（一个 `node_modules` 可能就有十万个文件）。

## 三、身份：为什么不能用路径当 id

```ts
// library-scan.ts:150-161
/** Stable id from the file path, so re-scans and moves keep identity. */
function idFor(filePath: string): string {
  const normalised = process.platform === 'win32' ? filePath.toLowerCase() : filePath
  let h1 = 0x811c9dc5
  let h2 = 0x01000193
  for (let i = 0; i < normalised.length; i += 1) {
    const code = normalised.charCodeAt(i)
    h1 = Math.imul(h1 ^ code, 16777619)
    h2 = Math.imul(h2 + code, 2246822519)
  }
  return `${(h1 >>> 0).toString(16)}${(h2 >>> 0).toString(16)}`
}
```

这段 12 行代码里有四个知识点：

**1. 为什么要有 id，直接用路径不行吗？**

路径能当 id，但会出三个问题：

- **太长**：`D:\Music\某专辑\01 - 某首歌.flac`，放进 URL、放进 Map、放进 DOM key 都很笨。
- **会变**：用户改了文件夹名，整库的身份就断了——播放历史、收藏、歌单全都对不上。
- **字符集麻烦**：中文、空格、`#`、`%` 在 URL 里要编码，编码一次出错就全错。

哈希成一个短字符串，问题一次性解决。

**2. 为什么两个哈希混在一起？**

`h1` 和 `h2` 用**不同的乘数**（`16777619` vs `2246822519`）和不同的混合方式（异或 vs 加法）。两路结果拼起来是 64 位。

原因是**降低碰撞概率**：单路 32 位哈希，在几万首歌的量级上，生日悖论算出碰撞概率已经不是零。两条独立的 32 位哈希，碰撞概率降到几乎不可能。

> 注意：这不是加密散列（不用 SHA-256 是因为它慢、而且要 import 一个模块）。**这是「足够好的短 id」，不是「安全哈希」**。用途不同，标准就不同。

**3. 为什么 Windows 要 `toLowerCase()`？**

```ts
const normalised = process.platform === 'win32' ? filePath.toLowerCase() : filePath
```

Windows 上 `D:\Music\a.mp3` 和 `d:\music\A.MP3` 是**同一个文件**。如果 id 不统一大小写，同一首歌会得到两个 id——重复条目、重复封面、历史错乱。

**这是「运行时平台差异」的经典处理**：不是写两个实现，而是**在进入算法前把输入规范化**。

**4. `Math.imul` 和 `>>> 0` 是什么？**

JS 的数字是 64 位浮点，`*` 在超过 2^53 时会丢精度。`Math.imul` 做的是**真正的 32 位整数乘法**（结果按 32 位取模），这正是哈希函数需要的。

`>>> 0` 是「无符号右移 0 位」，作用是把有符号的 32 位整数转成无符号（负数变正数）。`toString(16)` 遇到负数会输出 `-1a2b`，那是错乱的 id。

> 这两个都是「位运算在 JS 里的真实用途」。平时写业务代码用不上，**写底层算法时必须有**。

**一个诚实的限制**：注释说 "re-scans and moves keep identity"，但**改名/移动路径后，id 其实会变**（因为 id 由路径算出）。这句注释的意思是「重扫同一个路径时身份不变」。**读注释也要带着判断**——这是很好的练习素材。

## 四、元数据：脏数据的归一化

```ts
// library-scan.ts:163-172
function firstString(value: unknown): string {
  if (typeof value === 'string') return value
  if (Array.isArray(value) && typeof value[0] === 'string') return value[0]
  return ''
}

function toNumber(value: unknown): number | null {
  if (typeof value === 'number' && Number.isFinite(value)) return value
  return null
}
```

**为什么输入是 `unknown`**？因为 `music-metadata` 的返回类型本来就是「宽松的」：同一个字段可能是字符串、可能是数组（多艺术家）、可能是 `null`、可能是别的标签格式留下的奇怪东西。

两个函数各解决一类问题：

- `firstString`：**这是谁的歌？** 多艺术家时取第一个。空 → `''`（不是 `undefined`，因为 UI 渲染 `''` 很安全）。
- `toNumber`：**这个数值是真的吗？** `NaN`、`Infinity`、字符串 `"320"` 全拒掉。

`Number.isFinite` 是关键：`typeof value === 'number'` 会让 `NaN` 通过，而 `NaN` 一旦进入排序、求和、进度计算，会污染整条链（`NaN` 参与的任何算术结果还是 `NaN`）。

**这就是「防御性解析」的标准姿势**：

```
未知输入 → 窄化 → 保底值
```

不是「相信上游」，而是**在边界处一次性把形状校正干净**。后面所有代码都可以假定「字段类型是对的」。

紧接着的 `buildTrack`（第 174 行起）就是把这些归一化后的值组装成 `Track`——**组装逻辑里没有一个 `try/catch`，因为脏东西已经在门口被拦掉了**。

## 五、动态 import：为什么不在顶部 import

```ts
// library-scan.ts:107-110
async function metadata(): Promise<MetadataModule> {
  if (!metadataModule) metadataModule = await import('music-metadata')
  return metadataModule
}
```

`music-metadata` 是个**不小的解析库**。如果顶部静态 `import`，那么：

- 应用一启动就要加载它（哪怕用户从没扫描过）；
- 所有 import 了这个文件的代码都要付这个代价；
- 打包时它一定进主 chunk。

动态 import 把它变成**「第一次真正需要时才加载」**，而且缓存到模块级变量（第二次调用不重复 import）。

**判断标准**：这个依赖是否「每次启动都用得上」。用不上 → 延迟 import。

> 同一条思路在 `protocols/*.ts` 里也出现：那里延迟的是 `electron` 本身，目的不同（为了让裸 Node 测试能加载文件），但手法一样——**import 的时机是一个设计选择，不是语法细节。**

## 六、并发：8 个 worker 抢一个光标

这是全篇最值得反复读的一段：

```ts
// library-scan.ts:399-429
const results: ScannedTrack[] = []
const CONCURRENCY = 8
let cursor = 0

const worker = async (): Promise<void> => {
  while (cursor < files.length) {
    if (cancelled?.()) return
    const index = cursor
    cursor += 1
    const file = files[index]

    let stat: fs.Stats
    try {
      stat = await fs.promises.stat(file)
    } catch {
      continue          // 文件在这几秒里被删了：跳过
    }

    const cached = cache.get(file)
    if (cached && cached.size === stat.size && cached.mtimeMs === stat.mtimeMs) {
      results.push(cached)
      report({ cached: progress.cached + 1, current: file })
      continue
    }

    results.push(await readTrack(file, stat))
    report({ scanned: progress.scanned + 1, current: file })
  }
}

await Promise.all(Array.from({ length: Math.min(CONCURRENCY, ...) }, worker))
```

**为什么不是「分成 8 段，每段一个 worker」？**

因为读取速度不均匀：有的歌 3 MB，有的 80 MB（无损）。分段会导致**一段早早做完，另一段还在跑**——总体时间由最慢那段决定（木桶效应）。

**「抢光标」模式**：每个 worker 循环里做的第一件事是从共享计数器取下一个任务。

```ts
const index = cursor
cursor += 1
```

在 JS 里这两行是原子的（单线程，没有 await 插进来），所以不需要锁。**这是 JS 并发模型的直接红利**：只要不在中间 await，计数器就不会被抢坏。

> 如果写成 `await something(); cursor += 1`，两个 worker 就会拿到同一个 index——**多线程里要用锁的地方，在 JS 里只要「别在中间 await」**。这个坑极其隐蔽。

**`while (cursor < files.length)` 而不是 `for (const f of files)`**：因为共享光标。for-of 每个 worker 会遍历全部文件（8 倍重复工作）。

**`Math.min(CONCURRENCY, Math.max(1, files.length))`**：文件不足 8 个时，不要起 8 个空转的 worker。

## 七、增量：最便宜的两个字段

```ts
// library-scan.ts:417-422
const cached = cache.get(file)
if (cached && cached.size === stat.size && cached.mtimeMs === stat.mtimeMs) {
  results.push(cached)
  report({ cached: progress.cached + 1, current: file })
  continue
}
```

判据只有两个：**文件大小**和**修改时间**。

为什么这两个够？

- **改内容的文件，大小几乎总是变**（重编码、加封面、改标签）。
- **即使大小没变，mtime 也会变**（任何写入都会更新它）。
- 两个都不变 → 「几乎可以确定没改过」。误判概率极低，而且代价只是「少更新一次元数据」，不是数据损坏。

**为什么不用内容哈希？** 那需要把每个文件完整读一遍——就等于没用增量，慢十倍。

**这就是工程上的「足够好的判据」**：不追求绝对正确，追求**错误代价可接受**。

反过来，如果这个场景是「同步到云端」，两个字段就不够（时间戳可能被保留），得用哈希。**判据的严格程度由场景决定，不由技术决定。**

`stat` 本身也有代价（一次系统调用），所以放在 `readTrack` 之前——**先做便宜的判断，再做昂贵的操作**。

## 八、取消：一个闭包，每处检查

```ts
const { onProgress, cancelled } = options
...
if (cancelled?.()) return
```

`cancelled` 是一个**函数**（`() => boolean`），不是布尔值。原因：

- 布尔值传进去就固定了，cancel 之后 worker 看不到变化；
- 函数每次调用都去问最新的状态。

调用点：**每个任务开始前**。没有在 `readTrack` 中间检查——因为一次元数据读取通常很快（毫秒级），**在任务边界检查已经足够**。细粒度检查会引入「读到一半的数据」这种新的复杂性。

**取消的语义是「停下，保留已完成的部分」**：`results` 里已经有扫完的歌，最后照样 `saveIndex`。用户点取消，得到的是「扫了一半的可用库」，不是空。

> 对比一下另一种常见实现：取消时抛异常 → 整个扫描作废 → 用户白等五分钟。**这就是「取消」与「放弃」的差别。**

## 九、进度：UI 关注点，所以拆出去

```ts
// library-scan.ts:377-397
const progress: ScanProgress = { phase: 'walking', found: 0, scanned: 0, cached: 0, current: '' }

const report = (patch: Partial<ScanProgress>) => {
  Object.assign(progress, patch)
  onProgress?.({ ...progress })
}
```

三个细节：

**1. `phase` 三个值的含义**

| phase | 这段时间在干什么 | 用户看到什么 |
| --- | --- | --- |
| `walking` | 遍历目录，只数不读 | 「发现中… N 个文件」 |
| `reading` | 逐个读元数据 | 「读取中… M/N」+ 当前文件名 |
| `done` | 写索引 | 消失 |

**为什么要分阶段**：遍历阶段的总数**是逐渐增长的**（不知道一共有多少），读取阶段总数**固定了**。UI 在两种阶段该显示的东西完全不同。用一个 `progress: number` 是表达不了这种差异的。

**2. `Object.assign` + 展开复制**

`report` 先改本地对象，再把**副本**传出去。为什么复制？因为 `onProgress` 的接收方是 IPC，可能异步序列化；直接传引用，接收方看到的是「稍后又被改过的」对象。

**这是「跨边界传值要复制」的最小例子。**

**3. 进度是纯逻辑，所以它被拆到 `pure/scan-progress.ts`**

那个文件里有 `configureProgressTransport`（进度怎么出去，可替换）、`sendProgress`、`resetProgressThrottle`、`mainWindowVisibility`。**扫描器不知道 IPC 存在**——它只调 `report`。

好处直接体现在测试上：进度节流逻辑可以在裸 Node 里测，不需要起 Electron。

**10Hz 合并**也在那里：元数据读取可能 100/秒地报进度，IPC 每报一次就是一次跨进程序列化。合并到 10Hz，用户看到的一样流畅，开销降一个数量级。

**窗口不可见时还会进一步降频**（见文献 1 的 ticker 一节）——同一条原则。

## 十、两类缓存和它们的上限

```ts
// library-scan.ts:277-280
const artCache = new Map<string, EmbeddedArt | null>()
const ART_CACHE_LIMIT = 64
...
// library-scan.ts:304-307
const folderArtCache = new Map<string, string | null>()
```

两个缓存，都是**模块级 Map**（跨扫描存活），都有上限：

- **嵌入封面**（音频文件里内嵌的图片）：解析慢，所以缓存。
- **文件夹封面**（`cover.jpg`、`folder.png` 这类）：同一专辑的几十首歌共用一个，所以缓存。

两个设计点：

**1. 缓存 `null` 也是缓存**

`Map<string, EmbeddedArt | null>` —— 值为 `null` 表示「这个文件确实没有封面」。**如果不缓存 null，每个没封面的歌都要重新解析一遍**（而「没有」恰恰是最常见的情况之一）。

**2. 上限 64，满了就清**

```ts
if (artCache.size >= ART_CACHE_LIMIT) { ... }
```

没有上限的 Map 就是内存泄漏。扫描 5 万首歌、每张封面 200 KB，不设限会吃掉 10 GB。

64 这个数没有魔力，是「够覆盖一次连续的专辑扫描，又不至于占内存」的经验值。**缓存必须有淘汰策略，哪怕是最粗暴的「满了全清」。**

## 十一、索引：版本号是为了能改

```ts
// library-scan.ts:58
const INDEX_VERSION = 1
...
// library-scan.ts:431-436
const index: LibraryIndex = { version: INDEX_VERSION, scannedAt: Date.now(), roots, tracks: results }
await saveIndex(index)
```

`version` 字段现在等于 1，看起来没用。**它的用处在你改字段的那一天**：

```ts
// 将来某天
const index = await loadIndex()
if (index.version < 2) return rebuild(index)   // 旧索引：重建
```

这就是第 7 章 C3 题（给 Track 加字段）为什么危险——**旧索引里没有这个字段**。两个解法：

- 加 `?` 让字段可选（本项目多数做法）；
- 升 `version` 并重建。

**`scannedAt` 同理**：它不是给代码用的，是给人用的（排查「为什么列表是旧的」时第一眼要看的东西）。

**索引是应用自己的数据格式，就必须自己管兼容性。** 数据库有 migration，本地 JSON 索引也得有。

## 十二、为什么这些代码能裸 Node 测

回头看这个文件的依赖：

```ts
import fs from 'node:fs'
import path from 'node:path'
import { ... } from './pure/...'      // 纯函数
const metadataModule = await import('music-metadata')   // 延迟加载
```

**没有一行 `import 'electron'`。** 所以 `library-scan.ts` 可以在裸 Node 里被 import——虽然它需要真实的文件系统才能跑起来。

真正被拆到 `pure/` 的是更小的判断：

| 文件 | 拆出去的东西 | 为什么值得拆 |
| --- | --- | --- |
| `pure/library-paths.ts` | 哪些路径是合法的库根 | 纯字符串判断，安全边界 |
| `pure/library-discovery-rules.ts` | 跳过哪些目录、认哪些扩展名 | 纯集合判断，改规则要有测试 |
| `pure/scan-progress.ts` | 进度结构、节流、可见性 | 有状态但无 IO，可测 |
| `pure/media-cache-rules.ts` | Range 头解析 | 纯解析，边界多 |

**判断标准**：这段代码**有没有 IO**？没有 → 拆到 `pure/`，配测试。有 → 留在原地，靠集成验证。

> 这是一个可以到处套用的分解方法：**「有副作用的」和「做决定的」分开，前者难测所以做薄，后者易测所以做厚。**

## 十三、把这一篇收成清单

| 问题 | 答案 |
| --- | --- |
| 为什么用显式队列遍历目录？ | 深度不可控、可暂停、可计数、可换顺序 |
| 为什么 `pop` 而不是 `shift`？ | O(1) vs O(n)；扫描不关心顺序 |
| 一个目录无权限怎么办？ | 跳过继续，部分成功优于整体失败 |
| 大小写为什么要统一？ | Windows 不区分大小写，`path.extname` 比较区分 |
| 为什么要哈希成 id？ | 路径太长、会变、字符集麻烦 |
| 两个 32 位哈希为什么要用不同乘数？ | 降低碰撞概率（64 位组合） |
| `Math.imul` / `>>> 0` 干什么？ | 真 32 位乘法；转无符号以便 `toString(16)` |
| 元数据为什么用 `unknown` 接收？ | 上游形状不可信，边界处一次性归一化 |
| 为什么动态 import `music-metadata`？ | 不是每次启动都需要，延迟加载 |
| 8 个 worker 为什么抢光标而不是分段？ | 任务耗时不均，分段会被最慢的一段拖住 |
| 抢光标为什么不需要锁？ | JS 单线程，只要不在中间 `await` |
| 增量判据是什么？ | `size + mtimeMs` 都没变就复用 |
| 取消后已完成的部分丢弃吗？ | 不丢，照样写索引 |
| 进度为什么要分 phase？ | 遍历阶段总数在涨，读取阶段总数固定，UI 不同 |
| 缓存为什么要存 `null`？ | 「没有封面」是最常见情况之一，不存就每次重解析 |
| `INDEX_VERSION` 现在有什么用？ | 现在没用，改字段那一天才用 |

## 十四、延伸阅读

- **Node 官方 `fs` 文档**：重点读 `promises.readdir` 的 `withFileTypes`（省一次 `stat`）与 `promises.stat`。这两个 API 是整个扫描的地基。
- **Node 官方 `path` 文档**：`join` / `resolve` / `extname` / `sep` 的区别。路径处理是最容易写错的地方。
- **`music-metadata` 的 README**：看它「返回类型为什么宽松」的说明，就理解了本篇第四节的动机。
- **MDN · `Promise.all` 与并发**：理解「并发不是并行」，以及为什么 8 个 worker 在 JS 里是有效的（IO 等待时可以切换）。
- **FNV 哈希算法**（维基百科 `Fowler–Noll–Vo hash function`）：10 分钟读完，你就懂 `h1`/`h2` 那两行在干什么。
- **项目内**：`docs/maintenance.md` 有「索引损坏/字段变更」的处理说明，和第 7 章 C3 题配套读。

**建议的动手**：把 `CONCURRENCY` 从 8 改成 1，扫一个几百首的目录，感受时间差别；再改成 32，感受「没有更快」——**IO 并发有一个收益上限，超过只是增加内存压力**。这个实验花 5 分钟，比读十篇性能文章有用。
