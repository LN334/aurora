# 第 6 站：练习册 —— 从改一个数字到加一个功能

> 30 道题，五组，难度递增。
> **不要求一次做完，要求每题都跑起来看过结果。** 看懂和做出来是两件事。

## 怎么用这本练习册

1. **按顺序做。** A 组不做完不要碰 C 组——跨层改动需要先熟悉「改完怎么验」。
2. **每题都从干净状态开始。** 做之前 `git status` 确认工作区干净；做完 `git diff` 看自己改了什么；不想留就 `git checkout -- <文件>`。
3. **每题做完必须跑一次 `npm run typecheck`。** 到 C 组要跑 `npm run check`。
4. **卡住超过 40 分钟就看提示。** 提示不是答案，是方向。看完还想不明白，把问题写下来跳过——后面会懂。
5. **不要抄。** 本项目所有答案都藏在代码里：想加保护判断，先看 `electron/pure/app-paths.ts` 怎么写的；想加设置项，先看 `row-density.ts`。

每组开头有「这一组练什么」，做完回头看一眼，确认真的练到了。

# A 组 · 只改值（8 题）

> **练什么**：建立「改 → 跑 → 看」的循环，学会读代码找常量，学会用 `git diff` 管住自己的手。
> 全部是改一个数字、一个字符串、一个颜色。改完必须肉眼确认界面上真的变了。

### A1 · 换掉主色

**改哪里**：`src/styles/tokens.css` 里的 `--accent`（默认 `#7d8899`）。

**怎么做**
1. 改成 `#e0553f`（一个偏橙的红），保存。
2. 如果 `npm run dev` 已经把 Electron 起起来了，看窗口——Vite 的热更新会直接换色，不用重启。
3. 改回去。

**验收**：至少三个地方跟着变了（按钮、进度条、选中态）。如果只变了一处，说明有人硬编码了颜色——把它找出来，这就是一次小型 code review。

**卡住就看**：`grep -rn "#7d8899" src/` 看这个色值还被抄在哪。

---

### A2 · 把列表行改高

**改哪里**：`src/features/settings/row-density.ts` 的 `ROW_DENSITIES`。

**怎么做**
1. 三个档位现在大概是 `46 / 60 / 76`（单位 px）。把 `compact` 改成 `32`。
2. 在应用里把行密度切到「紧凑」，看歌曲列表。
3. 看封面图有没有被裁掉、文字有没有溢出。

**验收**：行变矮了但**文字没被切掉一半**。如果切了，说明这个高度是靠固定值撑的，去找对应的 CSS（搜 `--row-h-trk`），看 padding 是怎么算的。

**卡住就看**：这个文件里那个 `useSyncExternalStore` 模式——它是「值变了，所有用到的地方跟着变」的最小实现模板，C 组会照着抄。

---

### A3 · 改窗口初始尺寸

**改哪里**：`electron/main.ts` 里 `new BrowserWindow({...})` 的 `width` / `height`。

**怎么做**
1. 它们现在不是写死的数字，而是「命令行指定了就听命令行的，否则听上次关窗时记下来的尺寸」——找到那个 `state.width` 从哪来。
2. 给 `width` 加 200（比如 `state.width + 200`，注意别破坏原来的三元表达式）。
3. 先 `npm run build:electron`，再 `npm run dev`，看窗口。
4. 顺手看 `minWidth: 940` / `minHeight: 620`：把窗口拖到最小，验证这个下限真的生效。

**验收**：窗口更宽了，而且**拖不到比 940 更窄**。

**卡住就看**：改主进程代码不重启看不到效果（那是 Node 侧）；`npm run dev` 每次都会先 `build:electron`，所以重跑一次 dev 就够。

---

### A4 · 交叉淡化最长能多长

**改哪里**：`src/features/player/crossfade.ts` 的 `MAX_SWAP_MS`（现在 6000）。

**怎么做**
1. 改成 `12000`。
2. 读这个文件顶部的注释——它讲了一个真实 bug：上一版把「秒数」当成了开关，滑到 12 秒和 1 秒效果一样。
3. 跑 `node --test tests/crossfade.test.ts`，看有没有测试因此变红。

**验收**：测试结果你能一句话解释清楚。如果真的红了，**不要改测试去迁就代码**——先想明白是常量该改还是测试的假设该改。

**卡住就看**：这就是「常量被两处使用」的典型场景：一处是上限，一处是换算。改之前先 `grep -rn "MAX_SWAP_MS" src/`。

---

### A5 · 一次多画几行

**改哪里**：`src/ui/TrackList.tsx` 的 `PAGE` 和 `STEP`（第 40 行附近，现在是 120 / 200）。

**怎么做**
1. 把 `PAGE` 改成 `20`。
2. 打开一个几百首的歌单，看：初始只画 20 行，滚动到底部时再补 200 行。
3. 想清楚：这两个数字为什么不是一个？如果合成一个会怎样？

**验收**：你能说清 `PAGE` 和 `STEP` 各自的职责，以及「首屏快」和「滚动不卡」为什么需要两个不同的量。

**卡住就看**：搜索这两个常量在哪被使用；再读一下「为什么用 `NBSP` 占位」的注释（同一个文件里，讲的是行高不一致导致的抖动）。

---

### A6 · 让「空」的时候好看一点

**改哪里**：`src/ui/EmptyState.tsx` 的 props 与默认渲染。

**怎么做**
1. 这个组件的签名是 `EmptyState({icon, title, hint, action, stage})`。`stage` 为真时渲染的是另一套（极光背景）。
2. 把某个页面的空状态文案改成你自己的话（随便挑一个页面，搜 `EmptyState` 找调用点）。
3. 再把 `stage` 从 `false` 改成 `true`，看视觉差别。

**验收**：改文案和改视觉是两回事——`title` 是数据，`stage` 是行为。你能说清「哪些 props 该由调用方决定，哪些该由组件自己决定」吗？

---

### A7 · 安装后叫什么名字

**改哪里**：`package.json` 的 `build` 段（NSIS 相关配置）。

**怎么做**
1. 找到 `shortcutName`（或 `productName`），改成一个你喜欢的名字。
2. **不要打包**（`npm run dist` 很慢，而且会改产物）。
3. 只做一件事：改完跑 `npm run build`，确认构建没坏。

**验收**：你知道了「配置」和「代码」的区别：配置文件改错，构建立刻报错；代码改错，可能要跑到那一步才发现。

---

### A8 · 首帧的底色

**改哪里**：`electron/main.ts` 里 `backgroundColor: nativeTheme.shouldUseDarkColors ? '#0d1013' : '#f1f4f8'`。

**怎么做**
1. 读那段注释：窗口是 `show: false`，等 `ready-to-show` 才显示；开屏页已经去掉了，所以这层底色是首屏之前唯一可见的东西。
2. 把两个颜色改成一眼能认出来的（比如纯绿 `#00ff00`）。
3. 重跑 dev，**手快一点**看窗口刚出现的那一瞬间（或者把 `show: false` 临时改成 `true` 就更容易看到）。
4. 改回来。

**验收**：你亲眼看到了「那一层底色」。这个练习的意义是：**读注释能让你知道一个你没注意过的细节存在。**

# B 组 · 写纯函数 + 测试（8 题）

> **练什么**：把逻辑写成「输入 → 输出」的纯函数，再给它配测试。
> 这一组是编程能力真正的分水岭。会改值是会用工具，会写纯函数是开始写程序。

**B 组的通用流程**：写函数 → 在 `tests/` 下建同名测试文件 → `node --test tests/xxx.test.ts` → 红 → 改 → 绿。

### B1 · 给已有的纯函数补边界测试

**改哪里**：`tests/crossfade.test.ts`。

**怎么做**
1. 先读 `src/features/player/crossfade.ts`（15 行，很短）和它的四条测试。
2. 补两条：输入 `0` 和输入 `12`（超过上限）。
3. 跑测试。

**验收**：两条都绿，而且你能说出「为什么这两条值得测」。如果有一条红了——恭喜，你发现了真 bug（想想：超过上限时应该钳到上限，还是不淡化？）。

**卡住就看**：测试文件的写法——`node:test` + `node:assert/strict`，没有 jest 那套 `describe/it` 的仪式。

---

### B2 · 自己写一个 clamp

**改哪里**：新建 `src/features/player/clamp.ts`（或者你觉得更合适的位置）。

**怎么做**
1. 写 `export function clamp(value: number, min: number, max: number): number`。
2. 写测试覆盖四种情况：范围内、低于下界、高于上界、`min > max`（这个怎么办？自己定规矩，写进注释）。
3. 跑测试。

**验收**：测试全绿。**再想一个问题**：项目里已经有很多 `Math.max(0, Math.min(x, 1))` 这样的写法，要不要全换掉？（提示：不要。新抽象不应该为了统一而统一。）

---

### B3 · 格式化时长

**改哪里**：新建 `src/features/library/format-duration.ts`。

**怎么做**
1. 写 `export function formatDuration(seconds: number): string`。
2. 规矩你自己定，但要写清：`65` → `1:05` 还是 `01:05`？`0` → `0:00` 还是空字符串？`-1` 怎么办？`NaN` 怎么办？
3. 写测试，覆盖你定的每一条规矩。

**验收**：**先写测试再写实现**（这叫 TDD，试一次）。写完 4 条测试，实现会自然被这 4 条约束出来。

**卡住就看**：项目里肯定已经有类似函数（`grep -rn "padStart(2" src/`）。**写完再看别人的实现**——你会发现「边界情况怎么定」才是难点。

---

### B4 · 命令行参数的解析

**改哪里**：`electron/pure/invite-arg.ts`（12 行）+ `tests/` 下对应测试。

**怎么做**
1. 读 `inviteFromArgv(argv)`：它从命令行参数里找出邀请码。
2. 补测试：参数名大小写不同、有多个 `--invite`、值里带空格、`--invite` 后面什么都没有。
3. 每种情况先写下**你认为应该**的结果，再跑，看实际是什么。

**验收**：至少有一条「你以为 A 实际是 B」。**这一条就是收获**——它让你知道读代码和跑代码的差别。

---

### B5 · 安全函数必须测越界

**改哪里**：`tests/app-paths.test.ts`（已有就补，没有就建）。

**怎么做**
1. 读 `electron/pure/app-paths.ts` 的 `resolveAppAsset(root, requestPath)`（36 行）：它检查 `\0`、检查解析后的路径是否还在根目录内。
2. 补测试：`..\..\windows\system32\config\sam` 这种越界路径必须返回 `null`。
3. 再补一条：路径里带 `\0` 必须返回 `null`。

**验收**：两条都返回 `null`。**这个练习的意义**：安全不是「相信调用方」，是「在入口处挡住一切」。

---

### B6 · 找出重复并抽出来

**改哪里**：你自己找一处。

**怎么做**
1. 用 `grep -rn "Math.max(0" src/` 找找有多少处「不许小于 0」的手写判断。
2. 挑一处最明显的重复，抽成有名字的函数。
3. 用你 B2 写的 `clamp`。
4. 跑 `npm run typecheck`，确认没漏改。

**验收**：改完类型检查通过，功能不变。**不要大面积重构**——只动一处，先体验「小步改 + 随时能回退」。

---

### B7 · 写一个 LRC 解析器

**改哪里**：新建 `src/features/lyrics/parse-lrc-lite.ts` + 测试。

**怎么做**
1. LRC 的一行长这样：`[00:12.34]第一句歌词`。
2. 写 `parseLrc(text: string): Array<{ timeMs: number; text: string }>`。
3. 只需处理：时间戳解析、一行多个时间戳（`[00:01.00][00:05.00]同一句`）、空行跳过、乱码行跳过（**不要抛异常**）。
4. 写 6 条测试。

**验收**：6 条全绿，且第 4 条（乱码）不是靠 `try/catch` 兜住的，是靠判断跳过的。

**卡住就看**：这就是「解析」的本质——把字符串变成结构化数据，**并且对坏输入保持宽容**。真实项目里的歌词来自四个平台，脏数据是常态。

---

### B8 · 跑全量测试，并故意弄坏一次

**改哪里**：不改代码，只跑命令。

**怎么做**
1. 跑 `npm test`，记下总耗时和通过数。
2. 故意把一个纯函数改坏（比如把 `swapFadeMs` 的 `return` 改成固定值）。
3. 再跑 `npm test`，看失败信息长什么样——**记住这个格式**，以后你每天都会看到。
4. 改回来。

**验收**：你能读懂失败信息里的三件事：哪个测试、期望值、实际值。这三件事读懂，以后 80% 的调试靠它起步。

# C 组 · 跨层改动（7 题）

> **练什么**：一个功能不是改一个文件，是改一串文件，而且**每一层的类型都要对上**。
> 这一组开始有风险：会改到数据、会改到持久化、会让旧数据变成不兼容。

**C 组的通用流程**：`npm run check`（类型 + 测试 + 四个审计）。到这一组，红一次是常态。

### C1 · 加一个设置项：列表显示音质标签

**改哪里**：仿 `src/features/settings/row-density.ts` 抄一套。

**怎么做**
1. 新建 `src/features/settings/show-quality.ts`：照着 `row-density.ts` 写，一个布尔开关，key 用 `aurora.rows.quality`。
2. 在 `src/views/settings/panes/AppearancePane.tsx` 里加一个开关（找现成的行密度开关，放在它旁边）。
3. 在 `src/ui/TrackList.tsx` 里读这个开关，决定要不要显示音质标签。
4. `npm run check`。

**验收**：开关打开，列表出现标签；关掉，消失；**重启应用，开关状态还在**（这是 localStorage 的功劳，不是你的）。三处都通过才算完。

**卡住就看**：`row-density.ts` 里那个 `useSyncExternalStore`——它是「localStorage + React」的标准粘合法，照抄即可，别自己发明。

**风险**：直接在组件里 `useState` 会丢掉持久化；忘了 `subscribe` 会导致两个组件不同步。

---

### C2 · 加一条 IPC

**改哪里**：四处，缺一不可。

**怎么做**
1. 主进程：在 `electron/ipc/` 下找一个最近的文件，加一个 `ipcMain.handle('player:ping', () => 'pong')`。
2. `electron/preload.ts`：在对应分组里暴露 `ping: () => ipcRenderer.invoke('player:ping')`。
3. `src/env.d.ts`：在 `AuroraApi` 的对应组里加 `ping(): Promise<string>`。
4. 页面：随便找个地方调 `native.player.ping()` 并 `console.log`。

**验收**：打开 DevTools，看到 `pong`。**然后再试一次**：只删掉第 3 步的声明，看是编译报错还是运行时才发现（两者差别很大）。

**风险**：改了 `main.ts` 或 `ipc/*` 必须重跑 `npm run dev`（主进程不会热更新）。

---

### C3 · 给 Track 加一个字段并端到端贯通

**改哪里**：类型 → 扫描 → 索引 → UI。

**怎么做**
1. `src/types.ts` 的 `Track` 加一个字段（建议挑真的有用的，比如 `bitrateText?: string` 或 `comment?: string`）。
2. `electron/library-scan.ts` 生成 Track 的地方填上它。
3. `src/ui/TrackList.tsx`（或详情页）显示它。
4. `npm run check`。

**验收**：新扫描的歌有值，**旧索引里的歌没有值也不会崩**。

**风险**：这是本组最危险的一题。旧索引是磁盘上的 JSON，里面没有你新加的字段。**所有读这个字段的地方都必须容忍 `undefined`**——这就是为什么类型写成 `field?: string` 而不是 `field: string`。

**卡住就看**：`Track` 里那些带 `?` 的字段（`source?`、`albumId?`、`onlineId?`）就是历史层积的证据，每一个 `?` 背后都有一个「不能强制要求」的理由。

### C4 · 给扫描进度加一个字段

**改哪里**：纯函数 → 主进程 → 类型 → 界面。

**怎么做**
1. `electron/pure/scan-progress.ts` 的 `ScanProgress` 接口里加 `skipped: number`（现在有 `found / scanned / cached / current`）。
2. 找到所有构造 `ScanProgress` 的地方，补上这个字段（编译器会告诉你有哪些）。
3. 界面上显示它（搜索 `progress` 找到用到的地方）。
4. `npm run check`。

**验收**：扫描时能看到「跳过 N」。

**卡住就看**：这个文件里有个 10Hz 合并的节流——`sendProgress` 不是每次都发。读一下，理解「高频事件要合并」这个模式。

---

### C5 · 注册一个假平台

**改哪里**：`src/features/online/registry.ts` + 一个假实现文件。

**怎么做**
1. 新建 `src/features/online/providers/demo.ts`，导出一个 `OnlineMusicProvider`。
2. 能力全部设为 `false`，只实现搜索（返回假数据）。
3. 在 `registry.ts` 注册它。
4. 打开应用，看平台相关的界面有没有出现「Demo」。

**验收**：设置页的平台列表里出现了它（或者界面完全不认它——**这两种结果都要能解释**）。如果是后者，说明还有第二处地方在维护平台列表，去找出来。

**风险**：假 provider 可能让类型检查报「缺少方法」。这时候**不要瞎补空实现**，回去读 `types.ts` 里的接口，看清每个方法是干什么的、哪些是可选的。

---

### C6 · 播放页加一个「复制歌名」按钮

**改哪里**：一个组件 + 一个交互。

**怎么做**
1. 在 `src/views/NowPlayingPage.tsx` 找到显示歌名的位置，加一个按钮。
2. 点击时调 `navigator.clipboard.writeText(track.title)`。
3. 复制成功了给个提示（项目里有 toast 机制，搜 `toast`）。
4. 考虑：这首歌没加载时按钮该不该禁用？

**验收**：点了真的能粘贴出歌名；没歌的时候按钮是灰的或不存在。

**卡住就看**：找项目里已有的「复制」功能（`grep -rn "clipboard" src/`），照着它的失败处理写——剪贴板 API 在没有焦点的时候会失败。

---

### C7 · 加一个私有协议（选做，难）

**改哪里**：`electron/protocols/` + `electron/main.ts` + `index.html`。

**怎么做**
1. 照着 `media-protocol.ts` 抄一个最小协议 `aurora-note:`，只服务一个固定文本文件。
2. 在 `main.ts` 里注册它（注意 `registerSchemesAsPrivileged` 必须在 `app.ready` 之前，注册 handler 在之后）。
3. **`index.html` 的 CSP 里加上它**。
4. 页面里 `fetch('aurora-note://hello')` 看能不能拿到内容。

**验收**：拿到内容。**如果拿不到，按这个顺序排查**：协议注册了吗 → handler 挂了吗 → CSP 放行了吗 → URL 格式对吗。

**风险**：这题最容易卡在 CSP 上。四个失败点，任何一处不对都是静默失败（请求直接被拦，不报错）。

# D 组 · 架构理解（7 题）

> **练什么**：不写代码（或只写文档），练「看懂一座房子怎么盖的」。
> 这一组做完，你换到任何一个项目都能快速上手。

### D1 · 画架构图

**做什么**：A4 纸，画三层 + 五个接缝，标文件路径。

**验收**：不看文档能默画出来。画不出的部分，就是你没真懂的部分。

---

### D2 · 追一条调用栈

**做什么**：追「点了播放全部的按钮 → 第一首歌出声」的完整调用栈，写成 20 行文档，每行一个 `文件:行 函数()`。

**验收**：每一步都能点开文件对得上。对不上的说明你在猜。

**提示**：起点大概是 `player.playQueue`（`src/features/player/actions.ts:50`），终点是 `<audio>` 拿到 `src`。

---

### D3 · 用 grep 做一次 code review

**做什么**：项目的硬规则是「`features` 不许 import `views`」。用 grep 验证这条规则有没有被破坏。

```bash
grep -rn "from '../../views" src/features
grep -rn "from 'electron" src/features
```

**验收**：两条命令都没有输出（或者输出你能逐条解释）。**然后想**：如果这条规则被破坏了，会坏在哪？（提示：循环依赖、打包时把整个页面拖进来）

---

### D4 · 找出「为可测而拆」的证据

**做什么**：`electron/pure/` 下每个文件都是为了「能在裸 Node 里测」而从大文件里拆出来的。挑一个，找到它的原文在哪、被谁 import、测了什么。

**验收**：你能说清「拆出去」和「留在原地」的代价差别。

**示例**：`electron/pure/scan-progress.ts` 的注释说「`library-scan` 再导出它，所以扫描器还是干净的」——这就是答案的格式。

---

### D5 · 说清「四家平台共用一套页面」的机制

**做什么**：不看代码，用自己的话讲：为什么加第四家平台不用写第四个页面？

**验收**：你的回答里出现了「能力是布尔字段」「注册表」「provider 只回答数据不画界面」这三个意思。

**然后**：去看 `src/features/online/types.ts` 的注释，对照它写的三条原则，看你说漏了哪条。

---

### D6 · 读一条重构历史

**做什么**：`CHANGELOG.md` 里有很多「清理」「统一」「重构」的条目。挑一条，用 `git log --oneline` 找到对应提交，看那次改了什么。

**验收**：写 100 字说明「这次重构解决了什么问题」。**重点不是看懂 diff，是理解「为什么要动它」**。

---

### D7 · 提一个功能，写改动清单

**做什么**：想一个你真想要的功能（哪怕很小）。写一份清单：要改哪些文件、每个文件改什么、有什么风险、怎么验。

**验收**：清单里至少有一项是「我可能想错了，需要先确认」。

**这一题是整个练习册的终点**：能写出一份靠谱的改动清单，你就能独立开工了。写不出来，说明 A–C 组还没做透——回去挑几题重做。

# 附录 · 每题的自检三问

做完任何一题，问自己：

1. **我改的东西，是怎么被验证「真的生效」的？** 是肉眼看的，还是测试证明的？
2. **如果我不小心改坏了，怎么回到原状？**（`git checkout` 只会还文件，磁盘上的索引/缓存/设置还在，想清楚）
3. **这题里有没有一个「我照抄了但没真懂」的地方？** 有的话，回去把那三行读懂。

三个问题都答得出来，这题才算做完。
